# The same kernels on an A100, measured

docs/PERF.md is measured on an M2 and says so in its title. This file is the
other device: an **A100-SXM4-40GB**, Chrome 152, Dawn over Vulkan, NVIDIA
driver 535.129.03. It exists because "is this tuned only for Apple silicon?"
is a question the repository could not answer - every number in docs/PERF.md
comes from one machine, and several of its conclusions invert here.

Read this beside docs/PERF.md, not instead of it. Where the two disagree the
disagreement is the finding.

## Getting a WebGPU device at all, which is most of the work

🔴 **THE DEFAULT ANSWER TO `requestAdapter` ON LINUX/NVIDIA IS SwiftShader, AND
IT DOES NOT SAY SO.** Chrome answers with its software fallback, the page runs,
every kernel computes the right numbers, and a bench reads about a thousandth
of the device. `adapter.info.vendor` is `google` and `architecture` is
`swiftshader`; on the real device they are `nvidia` and `ampere`. **Assert on
that before trusting any number**, because nothing else in the stack will tell
you. Four things are needed together and they were found in this order:

1. `--enable-features=Vulkan --use-vulkan=native --use-angle=vulkan
   --ignore-gpu-blocklist`, or Dawn's Vulkan backend never comes up.
2. **A Vulkan loader new enough to know `VK_EXT_surface_maintenance1`.** Ubuntu
   22.04 ships 1.3.204, which predates the extension, so `vkCreateInstance`
   fails `-7` (`VK_ERROR_EXTENSION_NOT_PRESENT`) and Chrome falls back without
   a word in the page. LunarG's 1.4.313 loader fixes it.
3. **NO `--headless=new`.** Headless Chrome asks for `VK_EXT_headless_surface`,
   which the NVIDIA driver does not implement and Mesa's llvmpipe does - so
   headless is exactly what steers the adapter to software. It has to run
   HEADFUL, which on a GPU box means `Xvfb :99` and `DISPLAY=:99`.
4. A GPU the user can open. `/dev/nvidia0` is 0666 here, so no group change was
   needed; `/dev/dri/*` is not, and is not used.

`tools/gpu-chrome.mjs` now carries all of this behind `process.platform`, plus
`LOCALFOLD_CHROME` for the browser path - it was a hard-coded `/Applications`
string, which made every tool in `tools/gpu/` Mac-only.

🔴 **`shader-f16` IS OFF ON EVERY NVIDIA GPU BY DAWN POLICY, AND ONE FLAG
TURNS IT BACK ON.** Out of the box this adapter advertises 23 features and
`shader-f16` is not among them, so `chooseLinearKernel` takes its f32 branch,
`selectAttentionFlashKernel` picks `f32` over `chunk16`, and every `@f16` arm
in every bench reports `skipped` - most of this repository's fast path, simply
not running. **It is not the hardware and it is not the driver.**
`src/dawn/native/vulkan/PhysicalDeviceVk.cpp` states four conditions:

    HasExt(ShaderFloat16Int8) && shaderFloat16 && shaderInt16
      && storageBuffer16BitAccess

and this device passes all four - checked against the exact structs Dawn reads,
not the Vulkan 1.1/1.2 aggregates `vulkaninfo` prefers to print, because those
are different structs and only the former is what the code queries. Dawn
refuses anyway, several hundred lines further down, in a second gate that the
first gives no hint of:

    // TODO(crbug.com/42251215): Investigate f16 CTS test failures to enable on Nvidia.
    if (gpu_info::IsNvidia(mVendorId) &&
        !toggles.IsEnabled(Toggle::VulkanEnableF16OnNvidia)) { ... }

A blanket vendor block pending a CTS investigation. `--enable-dawn-features=`
**`vulkan_enable_f16_on_nvidia`** lifts it, the adapter advertises 24 features,
and `tools/gpu-chrome.mjs` now passes it on Linux. Worth **1.20x** on an
evoformer block on its own, below.

🔴 **AND THE CTS CAVEAT IS ANSWERABLE HERE, WHICH IS THE WHOLE POINT OF THE
DIFFERENTIAL SUITE.** Dawn turned it off because f16 CTS tests were failing, so
the flag is not a free lunch on trust. This repository can do better than trust:
its checkers compare against AlphaFold's own intermediates, at bounds set on the
M2. With the toggle on, all four AF2 gates pass, f16 arms included:

| checker | f32 arm | f16 arm | bound |
|---|---:|---:|---:|
| `check-evoformer-transition` | 2.18e-7 | **1.71e-3** | 4e-3 |
| `check-evoformer-attention` | 2.17e-7 | **1.24e-3** (chunk16) | 4e-3 |
| `check-evoformer-opm` | 2.25e-7 | - | 1e-5 |
| `check-triangle-residual` | 1.08e-7 | - | - |

and a 512-row fold moves mean pLDDT 58.775 -> 58.778. So on the kernels this
repository actually runs, at this repository's own tolerances, f16 on NVIDIA
holds. That is evidence about these kernels and not a general verdict on
Dawn's CTS failures - `check-evoformer-stack.js`, the one gate that compares a
whole stack against official values, cannot run here because its fixtures are
gitignored and absent from a fresh checkout.

🔴 **AND NO `chromium-experimental-subgroup-matrix` EITHER, FOR A SECOND DRIVER
REASON.** This driver exposes `VK_NV_cooperative_matrix` and not
`VK_KHR_cooperative_matrix`, which is what Dawn's Vulkan backend wants. So the
matrix-unit measurements in docs/PERF.md - the 1.15x-1.31x on AF2's dense
projection - cannot be reproduced or extended here at all. Worth noting that
docs/PERF.md's complaint that the M2 offers *"no f16-input, f32-accumulate
configuration"* is an Apple limitation: A100 tensor cores do exactly that, so
the ceiling that path is reaching for is much higher here than the M2's table
suggests. None of it is reachable through Chrome on this driver.

🔴 **AND THE CLOCK IS WHY EVERYTHING DRIFTS - IT IS FIXABLE, AND THAT CHANGES
THE METHODOLOGY.** CLAUDE.md says this machine drifts up to 3.2x between runs
and that arms must therefore be interleaved in one process. On an A100 the
cause is visible and removable: the GPU idles at **210 MHz** and boosts to
**1410**, a 6.7x swing, and `clocks_event_reasons.active` reads `0x1`, GpuIdle.

    sudo nvidia-smi -pm 1 && sudo nvidia-smi -lgc 1410,1410

Three separate `profile-af2-block.js` processes then read **12.73, 12.73,
12.75 ms**. That is 0.2%, so on this hardware **cross-process comparison is
valid** and the one-process constraint that shapes every bench here can be
relaxed. Before locking the clock, the same comparison moved kernels the change
could not touch by 20%, which is how the lock came to be looked for.

## This device's ceilings, and a probe that was measuring itself

🔴 **`probe-alu.js`'s VECTOR ARMS MEASURE THE SCALAR ARM'S WORK, ON BOTH
DEVICES.** Each arm builds eight chains of `a = a * m + b` in a `vecN` and then
stores `total.x`. Every other component is dead and the compiler deletes it, so
the vec2 and vec4 arms compute the scalar arm's arithmetic, take the scalar
arm's time, and are reported at 2x and 4x the GFLOP/s because the accounting
multiplies by `lanes`. `tools/gpu/probe-alu-lanes.js` runs both readings
interleaved - `.x` as the probe stores it, and a sum of every component:

| arm | ms | as priced |
|---|---:|---:|
| scalar | 30.4 | 18084 |
| vec2, `.x` only - probe-alu's arm | **30.5** | 36050 |
| vec2, all components | 60.6 | 18144 |
| vec4, `.x` only - probe-alu's arm | **30.5** | 72099 |
| vec4, all components | 120.4 | 18264 |

The real ceiling is **~18.1 TFLOP/s at every width**. Vectorising buys nothing
in ALU throughput here; it pays only where it reduces the instruction or access
count, which is what the kernels actually use it for. **The M2 numbers have the
same signature** - 1236 / 2420 / 4839 is 1x / 2x / 4x to three digits - so
docs/PERF.md's *"a vec4 multiply-add is 4x a scalar one"* and the *"quarter of
the vector ceiling"* that kernels are quoted against are almost certainly the
same artifact. Re-run `probe-alu-lanes.js` on the M2 before trusting either.

🔴 **AND THE PROBE IS UNDER-RESOLVED HERE AT ITS DEFAULT.** At
`--iterations=4096` all three FMA arms report exactly 2.40 ms, which is the
`performance.now()` floor around a submit rather than a measurement. The
ceiling only appears once the work does:

| iterations | 4096 | 32768 | 131072 |
|---|---:|---:|---:|
| fma f32 GFLOP/s | 7158 | 16559 | **18025** |

18.0 TFLOP/s is 92% of this card's 19.5 paper peak, so WGSL is not leaving
anything on the table. Quote a kernel against **18100**, not against 1236.

🔴 **AND THE f16 ARMS ARE BROKEN A SECOND WAY: THE CONSTANTS DO NOT SURVIVE THE
TYPE.** `probe-alu.js` steps `a = a * 1.0000001 + 1e-7`. In f16 those round to
exactly 1.0 and 0.0, so the step is `a = a`, the loop is hoisted whole, and the
f16 arms report **239 TFLOP/s** against this card's 78 non-tensor peak. With
constants that are representable - 1 + 2^-10 and 2^-10 - `probe-alu-lanes.js`
measures **36.0 TFLOP/s in f16 against 18.1 in f32, exactly 2.0x**, and the
same dead-lane artifact in its vector arms. The M2's recorded 1.7x does not
look degenerate, so Metal's compiler probably did not hoist it; the arm still
needs the fix on both.

Everything else, at `--iterations=131072`: workgroup reads **2768 G/s** (M2:
394), cached global f32 reads 2656 G/s, streamed vec4 143 G/s. The
arithmetic-to-workgroup-read ratio is 6.5 here and 3.1 on the M2, so a kernel
balanced on the M2 is somewhat more read-bound here - but only somewhat, and
the shape of `grid.attend`'s balance argument survives.

`probe-dispatch.js`: a dispatch costs **6.4 µs** in one pass, 8.4 in a pass
each, 45.9 in an encoder each. Cycling pipelines costs 11.9 uncached and 6.4
cached.

## The bus, which is free on unified memory and is not free here

🔴 **`writeBuffer` RUNS AT 1.24 GB/s AND A READBACK AT 1.01, WHILE A
DEVICE-TO-DEVICE COPY RUNS AT 32.7.** `tools/gpu/probe-bus.js`, at 78 MiB:

| | ms | GB/s |
|---|---:|---:|
| upload (`writeBuffer`) | 65.8 | 1.24 |
| readback (`mapAsync`, no copy out) | 22.9 | 3.57 |
| readback + `.slice()` into a Float32Array | 81.1 | **1.01** |
| device-to-device `copyBufferToBuffer` | 2.5 | 32.72 |

The `.slice()` is not incidental: a mapped range dies at unmap, so every caller
here copies out of it, and that host memcpy is 58 of the 81 ms. **On an M2 all
four rows are the same memory and none of this exists.** Any structure this
repository has priced as cheap because it was measured there needs re-pricing.

🔴 **AND `bench-grid-attend.js` IS 96% BUS ON THIS DEVICE, SO ITS NUMBER IS NOT
A KERNEL.** It times `Af3GridSelfAttentionGpu.run`, which uploads the whole pair
representation and reads the result back. `tools/gpu/bench-grid-attend-passes.js`
wraps the identical call in `profileDevice`:

| tokens | pair | wall | GPU passes | `attend` alone | off-device |
|---:|---:|---:|---:|---:|---:|
| 128 | 8.0 MiB | 22.7 ms | 0.52 | 0.18 | 22.2 (98%) |
| 256 | 32.0 | 74.3 | 2.26 | 1.14 | 72.0 (97%) |
| 400 | 78.1 | 168.8 | 8.13 | **5.10** | 160.7 (95%) |

So `grid.attend` at 400 tokens is **5.1 ms here**, not the 205 the bench prints
and not slower than the M2's 125.5 - the two numbers were never measuring the
same thing. Anything tuned against the printed number on a discrete GPU would
be tuning the PCIe bus. Tune with the pass profile.

🔴 **AND THE SAME SHAPE IS IN THE SHIPPING PATH, WHERE IT MATTERS MORE.**
docs/PERF.md already records that the diffusion head *"chains conditioning ->
encoder -> transformer -> decoder through Float32Arrays"* and costs four
host-device round trips a step, worth 19 ms of 71 on the M2 - and concludes
that the next thing there is chaining the stages on the device. On the M2 that
is a 27% item. Here the bus is ~30x slower relative to the compute, the sampler
runs the head 50 to 200 times, and **it is the first thing to do rather than
the next**.

## AF2, and a tile the row axis could not express

An evoformer block at 512 MSA rows and 59 residues, clocks locked, each figure
a separate process:

| | block | 48-block stack | vs the f32 start |
|---|---:|---:|---:|
| f32 only, shipped selection | 12.73 ms | 618 ms | 1.00x |
| ...plus the tile and softmax knobs | 11.68 | 561 | 1.09x |
| **f16 flag**, shipped selection | 10.59 | 508 | **1.20x** |
| f16 flag plus the knobs | **10.36** | **498** | **1.23x** |

against the 83.1 ms docs/PERF.md records on the M2 - so between **6.5x and
8.0x** depending on how much of the machine is switched on. The shape of the
profile is similar to the M2's: 65-72% dense GEMM, 19% the two flash
attentions.

🔴 **AND THE TWO KNOBS ARE WORTH MUCH LESS ONCE f16 IS ON, WHICH IS THE ORDER
THE LIST ABOVE IS IN.** They were first measured with the flag off, where the
tall tile carries the win; with it on, `chooseLinearKernel` takes its f16
narrow-tile branch and the tall tile never reaches the transitions at all, so
what is left is the softmax grouping - 1.09x becomes 1.02x. Both are still
right for the branch they are on, and `probe-tuning.js` still recommends both
(`agrees: true`) at 1.393x and 1.078x. **Measure a knob on the path the device
will actually take**, which is a thing this file got wrong once before
re-measuring.

🔴 **THE DENSE PROJECTION WANTS FOUR TIMES THE THREADS IT IS GIVEN, AND
docs/PERF.md SAYS THE OPPOSITE IN SO MANY WORDS.** `chooseLinearTile` notes that
*"halving the traffic AGAIN, with a 64-row tile of 128 or 256 lanes, is slower
at every shape measured - so this is not a bandwidth story and a third tile is
not the next move."* On this device a 128-row tile of 256 lanes is the fastest
arm there is. `bench-evoformer-linear.js`, first transition half, 30208 x 256 x
1024, all arms interleaved in one process, every one relRMS **0**:

| arm | tile | threads | ms | GFLOP/s | vs shipped |
|---|---|---:|---:|---:|---:|
| `16x16x8x4` | 128x64 | 256 | **1.067** | 14841 | **1.551x** |
| `32x16x4x4` | 64x128 | 512 | 1.083 | 14626 | 1.528x |
| `16x16x4x4` | 64x64 | 256 | 1.117 | 14176 | 1.482x |
| `8x8` | 64x64 | 64 | 1.217 | 13012 | 1.360x |
| `4x4` = `LINEAR_TILE` | 32x32 | 64 | 1.639 | 9663 | 1.010x |
| `4x8` = `LINEAR_TILE_WIDE`, what ships | 32x64 | 64 | 1.655 | 9571 | 1.000x |

14.8 TFLOP/s is 82% of this device's real ceiling; the shipped tile reaches 53%.

🔴 **AND THE FIRST ATTEMPT TO SHIP IT MEASURED 0.571x, WHICH IS THE TRAP
CLAUDE.md NAMES.** The transition dispatch is
`Math.ceil(rows / TRANSITION_TILE_ROWS)` where the column count comes from the
tile - and `TRANSITION_TILE_ROWS` is a module constant, `linearTileRows()`,
equal to LINEAR_TILE's 32. It is safe today only because **both shipped tiles
happen to have 32 rows**, which the comment beside it says outright. So the row
axis of the tile is frozen: any taller tile is dispatched ceil(rows/32) times
and recomputes its own rows, which is correct and redundant by the ratio - 4x
here, and it read as a 3.2x regression on the transitions. Threading
`linearTileRows(tile)` through `src/evoformer/block.js`,
`src/multimer/block.js` and `transition.js`'s own `encode` is what makes the
axis explorable at all. **No tile with a row count other than 32 has ever been
tried through the shipping path, on either device.**

🔴 **AND THE FLASH ATTENTION WANTS FOUR KEYS TO A RESCALE, WHICH NOTHING SHIPS.**
`createAttentionRegisterFlashShader` takes `group` and `vectorScore`;
`selectAttentionFlashKernel` passes neither, so every device gets `group: 1`.
`bench-msa-attention.js` at 512 queries, 59 batch, 8 heads:

| arm | ms | vs auto |
|---|---:|---:|
| `auto/g4v` | 1.494 | **1.226x** |
| `auto/g4` | 1.563 | 1.171x |
| `auto/g8v` | 1.706 | 1.073x |
| `auto` - what ships | 1.831 | 1.000x |
| `auto/g16v` | 2.037 | 0.899x |

Insensitive to the key chunk - 16, 32 and 64 all read 1.494-1.500 - so it is
the grouped rescale and not the staging. relRMS 3e-7 against the ungrouped arm.

🔴 **AND THE QUERIES-PER-INVOCATION KNOB IS A THIRD ANSWER, WHICH IS THE POINT.**
docs/PERF.md records q2 at **0.21x** and q4 at 0.12x on the M2, and upstream's
GB10 wanting q2 at 1.17x-1.42x. Here q2 is **1.000x** - free, neither win nor
loss - and q4 is 0.773x. Three devices, three answers, and this one has enough
registers that the spill the M2 records simply does not happen. Upstream
replaced their threshold with a probe; that is the right shape for this too.

🔴 **BOTH CHANGES COMPOSE, AND ONLY ONE OF THEM IS FREE.** `profile-af2-block.js
--sequences=512`, clocks locked, each a separate process:

| | block | 48-block stack | vs shipped |
|---|---:|---:|---:|
| shipped | 12.73 ms | 618 ms | 1.000x |
| tall tile | 12.12 | 582 | 1.050x |
| `g4v` only | 12.35 | 593 | 1.031x |
| both | **11.68** | **561** | **1.090x** |

`fold-af2.js --sequences=512 --recycles=1` is the gate. The tall tile is **bit
identical**: checksum -1397134 either way, every reported coordinate the same.
`g4v` is not - checksum -1409045, mean pLDDT 58.775 -> 58.753, the last alpha
carbon moving about 0.2 A - because it reassociates the online softmax, which
is the same class of difference the key-chunk arms already carry. It needs
`check-evoformer-attention.js` run across the axis before it ships, not a
stopwatch.

🔴 **AND NEITHER SHOULD BE SWITCHED ON UNCONDITIONALLY, BECAUSE THE M2 SAYS THE
OPPOSITE ABOUT THE FIRST.** docs/PERF.md's sweep has the taller tiles losing
there, and the shipped choice already turns on `shader-f16`, which this device
lacks. Two devices disagreeing about a tile is what a startup micro-probe is
for - the same conclusion upstream reached about the query knob.

## AF3, where the problem is that the problem is too small

`bench-head.js --profile`, one denoiser step, int5 bundle:

| tokens | wall | GPU passes | M2, from docs/PERF.md |
|---:|---:|---:|---:|
| 59 | 50 ms | 36.4 | 71 ms |
| 200 | 57 | 47.2 | 206 |
| 400 | 90 | 78.0 | - |

🔴 **THE STAGE TIMERS IN bench-head.js ATTRIBUTE GPU TIME TO WHICHEVER STAGE
AWAITS.** They report `atom-decoder: 48` of a 50 ms step at 59 tokens and
`transformer: 1`, while the pass profile puts 28 of 36 ms in the transformer's
own labels across its 24 blocks. The decoder is simply the stage that maps the
result back, so it absorbs everything queued behind it. Read `gpuPasses`, not
the stage row - and note that the gap between them, 50 against 36.4 ms, is the
bus again.

🔴 **THE DENOISER IS NOT HOST-BOUND, AND THE FIRST VERSION OF THIS FILE SAID IT
WAS.** docs/PERF.md's "what is left in a denoiser step is the four host-device
round trips" is stale: `diffusion-head-webgpu.js` chained its stages on the
device some time after that was written, and the four are gone. Measured rather
than inferred - `profileDevice`'s `summary()` reports the GPU's own span beside
the sum of its passes, so a bubble between passes is visible where a per-pass
total cannot see one:

| tokens | wall | GPU span | sum of passes | idle | submits |
|---:|---:|---:|---:|---:|---:|
| 59 | 43 ms | 41.25 | 39.64 | **1.61 (3.9%)** | 8 |
| 200 | 55 | 53.15 | 50.02 | **3.14 (5.9%)** | 8 |

The GPU is busy 96% of a step. There is no round trip left to remove, and an
earlier claim here of "18 ms a step of host overhead" was two numbers from two
different runs being subtracted.

🔴 **WHAT IS LEFT IS OCCUPANCY, AND THE TRANSFORMER'S DENSE PASSES DO NOT NOTICE
THE PROBLEM SIZE AT ALL.** From `bench-head.js --profile`, one denoiser step:

| tokens | `qkvg` | `ffw-wide` | `attend` |
|---:|---:|---:|---:|
| 59 | 8.27 | 4.23 | 1.10 |
| 150 | 8.33 | 4.41 | 4.13 |
| 400 | 8.82 | 5.13 | 24.20 |
| | **6.8x work, 1.07x time** | 1.21x | 22x, real |

`attend` is the only pass doing size-proportional work. Everything else costs a
FIXED ~28 ms a step whatever the protein is - which is not arithmetic, it is 24
blocks of dispatches too small to fill 108 SMs.

🔴 **AND THE TOKEN TILE IS THE KNOB, WHICH THE MODEL SIZES BY AN M2's ANSWER.**
`diffusion-transformer-webgpu.js` picks `min(4, fits(channels))` and its comment
records the sweep that chose it, ending: *"raising
maxComputeWorkgroupStorageSize bought nothing... the ceiling was never what
bound this, occupancy was"*. That sentence is exactly why the answer inverts
here - a smaller tile is MORE workgroups. On
`bench-diffusion-transformer.js`, against that default of 4:

| tokens | tile 4 (model's rule) | tile 2 | **tile 1** |
|---:|---:|---:|---:|
| 59 | 36 ms | 29 | **24 (1.50x)** |
| 150 | 52 | 45 | **44 (1.18x)** |
| 200 | 67 | **60** | 63 |
| 400 | 162 | **157** | 157 |

The win is largest where the protein is smallest, which is the shape occupancy
predicts, and `tile 8` at 150 tokens is 68 ms - the M2's direction taken
further, and worse. `diffusionTokenTile` in the device profile carries it; the
M2 keeps `null`, which is the model's own rule unchanged.

🔴 **AND IT IS BEHAVIOUR-PRESERVING, WHICH A RETILING SHOULD BE.** Two folds of
the oracle's own sequence, tile 1 against the model's rule, everything else
equal: `target_feat` 1.17e-2, `pair` 2.70e-2 and `single` 6.55e-3 against AF3
in BOTH, mean pLDDT 85.7 and pTM 0.740 in both, while the diffusion goes 1.6 ->
1.3 s. (Those relRMS figures are the int5 bundle's, not the f32 one
docs/PERF.md quotes 3.94e-4 for; the number that carries across is mean pLDDT
85.7 against its recorded 85.6.)

## The rest of the M2's occupancy constants, swept

Two knobs above turned out to matter. The pattern behind them is worth stating
on its own, because it generates the rest of this section: **every constant in
this repository that sizes a dispatch was calibrated on a device with ten
cores, and this one has 108.** The clearest is in `singleProjectSplits`, whose
comment says outright that its rule returns "the smallest split that reaches
about **110 workgroups**".

🔴 **AND WHICH WAY A TILE WANTS TO MOVE IS NOT A PROPERTY OF THE DEVICE.** It
depends on whether the dispatch already fills it. The diffusion transformer
runs 8 to 50 workgroups and wants a SMALLER tile; the triangle runs 10,000 to
40,000 and, if anything, a bigger one. Both are the same machine. Asking "is
this device big" gets it wrong half the time; asking "does this dispatch fill
this device" does not.

| kernel | shipped | best here | on the kernel | taken |
|---|---|---|---:|---|
| diffusion token tile | 4 | **1** | 1.50x at 59 tokens | **yes** |
| single projection splits | 110-workgroup rule | **1200-workgroup rule** | 1.46x-2.50x | **yes** |
| `grid.project` row tile | 8 | 8 (4 ties) | - | already right |
| AF3 `pair-transition` | 8:128 | 16:128 | 1.01x, noise | no |
| triangle projection tile | 32x16 | 32x32 by the bench | 1.14x | **no - see below** |

🔴 **THE SINGLE PROJECTION IS 1.46x-2.50x AND ABOUT ONE PERCENT OF A TRUNK.** It
is taken because it is free and exact, not because it is visible: a fold's
pairformer does not move outside noise. Recorded so the next reader does not
re-measure it expecting more.

| n | shipped | best | |
|---:|---|---|---:|
| 59 | splits 2, 0.1422 ms | splits 6, 0.0578 | **2.46x** |
| 128 | splits 1, 0.1406 | splits 6, 0.0563 | **2.50x** |
| 200 | splits 1, 0.1422 | splits 6, 0.0734 | 1.94x |
| 400 | splits 1, 0.1594 | splits 3, 0.1094 | 1.46x |

The same rule with the target at 1200 and the candidate list reaching 6 picks
the best arm at all four, so only the two numbers change and not the rule.

🔴 **AND THE TRIANGLE TILE IS A BENCH THAT MEASURES A KERNEL NOTHING RUNS.**
`bench-triangle-project.js` puts 32x32 ahead of the shipped 32x16 by 1.14x at
200 and 400 tokens at relRMS 0 - and in the pipeline it is worth nothing:
**762 ms of pairformer against 758** at 240 tokens, and 812 against 808 on a
repeat. The bench builds the triangle with `residual=false` and its own
unaliased buffers; the AF3 pair track runs `residual=true` against packed,
aliased scratch. Same function, different kernel, and the tile ranking does not
survive the difference.

🔴 **AND A FIRST RUN OF THE SESSION IS NOT A MEASUREMENT.** The A/B above first
read **994 ms against 854**, which is a 1.16x loss and looked like a real
result. It was shader compilation and the weight upload landing in whichever
arm went first; the same pair repeated twice afterwards ties to within 4 ms.
Any fold-level comparison needs a discarded first run, which the kernel benches
already do and `fold.js` does not.

🔴 **AND A BENCH ARM CAN NAME SOMETHING THE MODEL DOES NOT SHIP.** In
`bench-triangle-project.js` a bare "32x16" arm sets the projection AND the
contraction tile to 32x16, while the shipped pair is projection 32x16 with
contraction 32x32. So the arm labelled with the shipped tile is not the shipped
configuration, and the first comparison run here was against a straw man that
made 32x32 look 1.20x-1.29x better than it is. `32x16@32x32` is the arm that
means "what ships".

## One switch for the whole f16 path

`--f16=off` on any tool under `tools/gpu/`, or
`setHalfPrecision(device, false)` from code.

🔴 **"DOES THIS DEVICE HAVE THE FEATURE" AND "SHOULD THIS FOLD USE IT" WERE THE
SAME EXPRESSION, IN ELEVEN PLACES.** `device.features.has("shader-f16")` was
asked separately by AF2's transition and attention, AF3's pairformer block and
diffusion transformer, and ESMFold2's trunk and diffusion - so there was no way
to answer the second question differently from the first, and no way to compare
the two paths except by relaunching the browser with a different Chrome flag.
On a machine that drifts, two arms measured in two processes are not a
comparison at all, which is this repository's own rule.
`halfPrecisionAvailable(device)` is now the single place the shipping paths
ask, and `tools/gpu-chrome.mjs` turns `--f16=` into a `setHalfPrecision` call
before the entry module runs, so **every tool has the arm for free**.

🔴 **AND IT GATES AUTOMATIC SELECTION ONLY.** A caller that explicitly names a
precision - every bench arm, every differential checker that forces one - still
gets it, because forcing is exactly the case the switch is not about. The
`throw`s that guard an impossible request still test the device feature
directly.

🔴 **AND THE FIRST THING IT MEASURED IS THAT THE BLOCK NUMBER UNDERSTATES THE
FOLD BY A LOT.** An AF2 evoformer block moves 11.73 -> 10.28 ms, 1.14x. A whole
AF3 fold, 60 tokens and 50 diffusion steps, same process pair, clocks locked:

## bfloat16, asked and answered

🔴 **THERE IS NO bf16 IN WGSL, AND NO TENSOR-CORE PATH THROUGH ONE.** Neither
`enable bf16;` nor a `chromium_experimental_` spelling compiles; Dawn contains
no BF16 at all, and its subgroup-matrix component types are F32, F16, U32,
I32, U8 and I8. So bf16 cannot be COMPUTED in on any device a browser reaches,
and the A100's bf16 tensor cores are not addressable even in principle. The
question is therefore only about STORAGE, where a bf16 is the top sixteen bits
of an f32 and costs four instructions of core WGSL with no device feature -
the same niche `src/runtime/storage.js` already fills with `pack2x16float`.

🔴 **AND AS A STORAGE FORMAT IT LOSES TO WHAT IS ALREADY HERE, BY EXACTLY THE
MANTISSA.** `tools/gpu/probe-bf16.js` round-trips both formats over the ranges
a fold actually holds:

| band | f16 | bf16 truncate | bf16 round-to-even |
|---|---:|---:|---:|
| activations, \|v\| ~ 1 | **2.13e-4** | 3.41e-3 | 1.71e-3 |
| logits, \|v\| ~ 30 | **1.92e-4** | 3.06e-3 | 1.53e-3 |
| weights, \|v\| ~ 0.05 | **2.07e-4** | 3.33e-3 | 1.66e-3 |
| beyond f16's 65504 | **99.3% inf** | 3.47e-3 | **1.74e-3** |
| below f16's normal minimum | **3.00e-2** | 3.18e-3 | **1.59e-3** |

Eight times worse wherever f16 works, which is three mantissa bits exactly.
bf16 wins only at the two ends, and it wins there completely - 65107 of 65536
values became infinite in the f16 arm past 65504, and f16's error at 1e-6 is
140x bf16's.

🔴 **AND NOTHING HERE IS AT THOSE ENDS, WHICH IS WHY THE ANSWER IS NO.** The
range-critical state this repository has identified - "the running max, the
running sum, the logit and the accumulators" - is held in f32 REGISTERS inside
the flash kernel, not in a storage tensor, so there is no buffer waiting for a
wide-range narrow format. Everything that IS in storage is a post-LayerNorm
activation at |v| ~ 1 or a weight at ~0.05, and both bands are the ones f16
wins by 8x. The f16 storage decisions already recorded here were tight - the
pair scratch was UNPACKED because packing cost a factor of 1200 on the
confidence head - so a format eight times looser again has nowhere to go.

**The one thing that would change this** is a tensor whose dynamic range
actually exceeds f16, silently clipping today. Nothing measured says there is
one, and nothing has looked; a max-absolute-value pass per tensor over a real
fold is what would settle it, and is worth more than the bf16 question that
prompted it.

🔴 **AND A ROUNDING MODE IS NOT A DETAIL: round-to-nearest-even is exactly 2x
truncation**, everywhere, for one add and a mask. Truncating is the version
somebody reaches for first because it is one shift.

🔴 **AND THIS DEVICE FOLDS `unpack2x16float(pack2x16float(x))` INTO THE
IDENTITY.** The first version of this probe did the round trip in one
expression and reported **relRMS 0 in every band** - including values past
65504, which cannot survive an f16 - because the compiler removed the pair.
Packing and unpacking have to be separated by a buffer, which is what the
shipping code does anyway and is why its rounding is real. But a CHECKER that
validates a packed format in one expression would report perfect agreement and
be testing nothing, which is the same shape of fault as a checker that builds
its own kernel.

## Choosing a path per device, which is now a mechanism

`src/runtime/device-profile.js`. The question it answers is "Apple here, NVIDIA
there" - and the measurements say the vendor is the WRONG axis to hang it on,
so it resolves three ways instead, most trustworthy first.

🔴 **CAPABILITIES FIRST, BECAUSE THE API STATES THEM AND A NAME DOES NOT.**
`device.features.has("shader-f16")` is a fact; "this is an NVIDIA card, so it
has f16" is false on this exact machine and true on the same silicon under a
newer driver. `chooseLinearKernel` was already written this way and should stay
that way. Anything the API will tell you must not come from the table.

🔴 **THEN A MEASUREMENT, FROM `tools/gpu/probe-tuning.js`.** It races the two
tile arms and the two softmax arms in one process, interleaved, checks each arm
against the other, and prints the `Tuning` object this device should get.
`setDeviceTuning(device, ...)` is how an answer arrives. On this A100 it reads
the tile at **1.393x, relRMS 0** and the softmax at **1.235x, relRMS 3.07e-7**,
and recommends exactly the prior the table already holds - `agrees: true`.

🔴 **AND ONLY THEN AN ARCHITECTURE PRIOR, WHICH IS THE WEAK ONE.** Keyed on
`adapter.info.architecture`, falling back to `vendor`. It exists so a first
fold on a known part is fast without a probe, and every entry carries the
measurement it came from. It is weak because `adapter.info` is **two usable
fields, not four**: outside `--enable-webgpu-developer-features` the browser
blanks `device` and `description` for fingerprinting reasons - this A100
reports `{vendor: "nvidia", architecture: "ampere", device: "", description:
""}` normally - so a prior can name a generation and never a card.

🔴 **THE DEFAULT IS TODAY'S SHIPPED PATH, AND THAT IS WHAT MAKES IT SAFE.**
`DEFAULT_TUNING` is every knob at the value the code used before it was a knob,
and **there is deliberately no `apple` entry** - the M2's answers ARE the
defaults, and a second copy of them is a second thing to drift. Checked rather
than asserted: with the `ampere` prior disabled, this device measures 12.72 ms
a block against the 12.73 it measured before any of this existed, and
`fold-af2.js` returns checksum -1397134 with every coordinate unchanged. An
unrecognised device cannot regress, so adding a prior is a change to one device
instead of a risk to all of them.

🔴 **AND `adapter.info` DOES NOT SURVIVE ONTO THE DEVICE**, which is why
`recordAdapter(device, adapter)` sits in `requestAlphaFoldDevice` - the one
place both are in scope. A device built any other way (a test, a bench that
rolls its own) has no identity and gets the defaults, which is the right
failure.

🔴 **AND THE PROFILE KNOWS WHEN IT IS NOT A GPU.** `profile.software` is true
for SwiftShader and llvmpipe. Given how easily Chrome hands out the software
adapter on this platform, a bench should refuse to report a number rather than
quietly publish one taken at a thousandth of the speed.

What is wired through it today, and what each cost:

| knob | default (M2) | `ampere` | kernel | block | fold |
|---|---|---|---|---|---|
| `linearTallTile` | false | true | 1.55x | 1.05x | **bit identical** |
| `attentionGroup` / `attentionVectorScore` | 1 / false | 4 / true | 1.22x | 1.03x | pLDDT 58.775 -> 58.753 |
| `attentionQueriesPerLane` | 1 | 1 | - | - | - |

The third is in the object with no prior behind it because it is the clearest
case for the mechanism and the clearest case against a table: M2 0.21x, M4 Pro
0.45x, GB10 1.17-1.42x, this A100 1.000x. Nothing about the badge predicts it.

## The native JAX baseline, on this same A100

🔴 **THIS SECTION IS `openbind0`, NOT AlphaFold 3, AND LocalFold RUNS AlphaFold
3.** Every ratio below compares a port of one model against a native run of
another. The like-for-like numbers are in "AF3 against AF3" further down, and
they are the ones to quote.

🔴 **AND ITS METHOD IS WRONG TOO, NOT JUST ITS MODEL.** An earlier revision kept
this section on the grounds that "the method and the traps in it are right".
The method is what is wrong: every diffusion figure below - the 0.167 s and
0.745 s per "200-step sample", and the 51x and 17x built on them - comes from
differencing `--num_diffusion_samples`, which is a `vmap` axis rather than a
trajectory. It understates a 200-step diffusion by about 10x. The `--steps`
sweeps in "AF3 against AF3" replace all of it. What survives here is the SETUP
(uv sync, build_data, empty MSAs) and the two traps that are real: JIT is most
of a first call, and `--num_recycles=1` is two trunk passes.

What to aim for. `sokrypton/alphafold3` at `af3-any-model`, model `openbind0` -
the same graph, and Apache-2.0 weights rather than DeepMind's, so no terms
question. Matched to `fold.js`'s defaults as closely as the runner allows: one
seed's steady-state call, 200 diffusion steps, one diffusion sample, one
recycle (the flag refuses 0), token bucket set tight so JAX is not padding.

🔴 **SETUP, WHICH IS FOUR THINGS AND ONE SURPRISE.** `uv sync --no-editable`
(the editable build hits a scikit-build-core metadata mismatch), then
`.venv/bin/build_data` to generate the 545 MB CCD pickle the wheel does not
ship, then `--run_data_pipeline=false` with empty `unpairedMsa`/`pairedMsa` so
no databases are needed. The surprise is that **`jax==0.10.2`'s CUDA 12 wheels
run on this 535 driver** - CUDA minor-version compatibility holds, and no
driver upgrade was needed for the baseline either.

🔴 **AND JIT IS MOST OF A FIRST CALL, SO THE FIRST SEED IS NOT THE NUMBER.**
Seed 42 takes 42.85 s and seed 43, in the same process against the same shapes,
takes **2.14**. Give the input two `modelSeeds` and read the second.

| | 60 tokens | 240 tokens |
|---|---:|---:|
| **native JAX, total** | **2.09 s** | **3.14 s** |

🔴 **AND `--num_recycles=1` IS TWO TRUNK PASSES, NOT ONE.**
`model.py`'s `num_trunk_passes` returns `num_recycles + 1` for every model but
chai1, and it is a named function with a test precisely because getting it
wrong is invisible. So the run above gave JAX **twice** `fold.js`'s trunk work

🔴 **AND SWEEPING BOTH KNOBS SEPARATES THREE COSTS, NOT TWO.** Samples are

per-call cost. At 60 tokens, `--num_recycles` 1/2/3/5 measures 2.09 / 2.16 /

**The intercept is overhead, not trunk.** An earlier version of this file put
the whole 1.92 s against the trunk and concluded the trunk was at parity. It is
not: the trunk is 30 ms a pass at 60 tokens, and the recycle sweep is what says
so - four extra passes cost 0.12 s.

🔴 **SO THE COMPUTE GAP IS 9x TO 50x, AND THE 4.6x ON TOTALS WAS FLATTERING
US.** Per unit of the same work:

|---|---:|---:|---:|---:|
| | LocalFold | JAX | LocalFold | JAX |
| trunk, one pass | 1.2 s | 0.030 | 1.7 s | 0.195 |

The totals differ by only 4.5x-4.7x because JAX carries about **1.9 seconds of

🔴 **AND BOTH GAPS NARROW BY 3x-4x FROM 60 TOKENS TO 240**, which is the

🔴 **AND LocalFold's DENOISER BARELY NOTICES THE PROTEIN.** Per step: 43 ms at

🔴 **AND AF3's OWN CODE NAMES THE TWO THINGS IT DOES DIFFERENTLY**, in

already on this list, and the baseline prices it: **five samples cost JAX
6.12 s at 240 tokens where LocalFold would need five folds, 62.5 s.**

## AF3 against AF3, which is the comparison that was not being made

🔴 **THE BASELINE ABOVE IS A DIFFERENT MODEL FROM THE ONE LocalFold RUNS.** It
was taken on `openbind0`, chosen for its Apache-2.0 weights so there was no
terms question; `model-af3-int5/manifest.json` says
`model: {name: "alphafold3"}` and `source: AF3-lineage parameters from
af3.bin.zst`. So every ratio in that section compares a port of AF3 against a
native run of something else. Re-taken here on **AlphaFold 3 both sides**, with
DeepMind's own weights (academic use), on the driver this box now runs.

Same 68-token sequence `fold.js` folds by default. Every setting matched on
both sides with
`tools/oracle/bench_af3_native.py`: **one trunk pass, one diffusion sample, one
MSA row, 68 tokens with no bucket padding**, steady-state call, median of five
on the JAX side and median of four warm folds on ours.

🔴 **AND THE STOCK RUNNER DOES NOT DEFAULT TO ANY OF THAT, IN FIVE SEPARATE
WAYS.** Each was measured rather than assumed, and only ONE of the five - the MSA row
count - turned out not to matter. LocalFold's side of the sample row is not a default but a fact of the
code: `samples` exists only inside `diffusion-transformer-webgpu.js` and is
referenced by neither the head, the sampler nor `fold.js`, so a fold is
structurally one sample.

| what the CLI does | what LocalFold does | worth |
|---|---|---:|
| `--num_recycles` is `lower_bound=1` and passes are `num_recycles + 1`, so its FLOOR is two trunk passes | `recycles: 0`, one pass | **22.9 ms** |
| `steps` is not a flag at all; `config.heads.diffusion.eval.steps` is 200 | `--steps` | **8.14 ms each** |
| `evoformer.num_msa` is **1024**, so one sequence still runs the MSA stack over 1023 rows of padding | one row | **0.5 ms** |
| the default bucket list pads 68 tokens to **128**, and the pair track is quadratic | exact | *3.5x the pair work if left in* |
| `--num_diffusion_samples` defaults to **5** | one sample, structurally | **+656 ms at 200 steps, +39%** |

The MSA row count is the surprise: it is the mismatch that looks most alarming
and it is worth **0.9%**. The token bucket is the one nobody thinks to check and
it would have invalidated the whole comparison.

🔴 **AND DO NOT PRICE THE DIFFUSION BY SWEEPING `--num_diffusion_samples`. THIS
FILE DID, AND WAS WRONG BY 9.4x.** `diffusion_head.py` is

    apply_denoising_step = hk.vmap(apply_denoising_step, in_axes=(0, None), ...)

so samples are a BATCH AXIS INSIDE one denoising step, and the `scan` over
`config.steps` runs once however many samples there are. Going from 1 to 5
samples widens each kernel's leading dimension; it does not add four more
200-step trajectories. At 68 tokens those kernels are tiny, so the marginal
sample is nearly free - 0.175 s - and dividing it by 200 gave "0.875 ms a
diffusion step" where the truth is 8.14. The next entry prices that gap
exactly. **Sweep `--steps`.** 1 / 2 / 5 / 20 /
50 / 200 measure 55.0 / 60.8 / 85.9 / 209.3 / 459.4 / 1673.5 ms: a fit of
**46.8 ms + 8.14 ms a step**, which predicts the 50-step arm to 1.3% over a
200x range.

🔴 **AND THE SAMPLE SWEEP UNDERSTATES BY 10x FOR A REASON THAT CAN BE WRITTEN
DOWN.** Fitting both sample counts over `--steps` at 68 tokens:

| | fixed | a step |
|---|---:|---:|
| one sample | 46.8 ms | **8.14** |
| five samples | 53.2 ms | **11.43** |

Five samples cost **1.40x** one sample per step - that is what the `vmap` buys.
So the MARGINAL sample is `(11.43 - 8.14) / 4` = **0.82 ms a step against the
first sample's 8.14, which is 9.9x cheaper**. The superseded section divided
0.175 s by 200 and got 0.875 ms a step: that is the marginal number to within

priced a marginal vmap lane and called it the diffusion. And the 9.9x between

🔴 **SO THE DIFFUSION IS NOT THE GAP, AND THIS FILE HAD IT EXACTLY BACKWARDS.**
Earlier revisions said 33x on the diffusion against 12x on the trunk and ranked

🔴 **AND 90% OF A FOLD IS NOT A COMPUTE PASS.** `fold.js --steps=1 --profile`

costliest labels are ordinary and small: `grid` 24 ms, `tri` 22, `single` 14,

attacking, because the whole list is a tenth of the fold.

🔴 **AND THE OTHER 90% IS BUFFER TRAFFIC, WHICH `--f16=off` PROVES BY
DOUBLING IT.** `tools/gpu/profile.js` wraps `beginComputePass` and nothing else,
so its 144 ms excludes `writeBuffer`, `copyBufferToBuffer`, `mapAsync` and
buffer creation as well as host JavaScript - which left "host work" as a
hypothesis rather than a measurement. Forcing the f32 path settles it:

| 68 tokens, one step | `--f16=on` | `--f16=off` |
|---|---:|---:|
| compute passes | **144 ms** | **148 ms** |
| of wall | 1395 | **4267** |
| share | 10% | **3%** |
| GPU peak | 476 MiB | 855 MiB |

**Doubling the byte width added 2.87 SECONDS of wall and 4 ms of compute.** The
kernels barely moved - `grid` 24 -> 25, `tri` 22 -> 25, `single` 14 -> 17 - so
whatever the fixed cost is, it is:

- **not compute**, because the compute total did not change;
- **not host JavaScript**, because JavaScript does not care whether a buffer
  holds f16 or f32;
- **byte-proportional work outside a compute pass** - creation, upload, copy.

Non-compute goes 1251 -> 4119 ms, **3.29x for a 2x width**, so it is slightly
superlinear in bytes: allocation rather than pure transfer. That is the same
shape as the unconfirmed "buffer creation costs ~0.78 ms/MiB" note elsewhere in
this file, and it makes buffer reuse across folds the first thing to try.

🔴 **AND THE 90% IS THE TRUNK'S WEIGHTS BEING RE-UPLOADED EVERY FOLD. 1.95x.**
Three hypotheses died before this one and each was stated too confidently, so
the order is worth keeping. `--f16=off` costs 2.87 s of wall and 4 ms of
compute, which says the remainder is bytes; so the guess was allocation, then
per-dispatch host work. `tools/gpu/fold.js --buffers` (tools/gpu/buffer-profile.js)
prices every WebGPU call and refutes both:

| 68 tokens, one step | ms | calls | bytes |
|---|---:|---:|---:|
| `writeBuffer` | 144 | 1341 | 561.4 MiB |
| `mapAsync` | 125 | 37 | 53.3 MiB |
| `createBindGroup` | 9 | 2101 | - |
| `computePass(encode)` | 5 | 2101 | - |
| **`createBuffer`** | **4** | **1238** | **1274.7 MiB** |
| `queue.submit` | 3 | 192 | - |

**Allocation is free** - 1.27 GiB in 1238 calls for 4 ms, so the "~0.78 ms/MiB
buffer creation" note is dead - and **per-dispatch host work is 14 ms across
2101 dispatches**. Every API call sums to 290 ms; with the 144 ms of compute
that is 434 of 1300, and **67% is in no WebGPU call at all**.

🔴 **BECAUSE IT IS THE HOST WAITING FOR THE QUEUE, WHERE TRANSFERS LIVE AND
TIMESTAMPS CANNOT REACH.** `pairformer-block-webgpu.js` already said so - "the
host encodes a whole 48-block pass in about 5 ms and spends the rest inside
onSubmittedWorkDone" - and what it is waiting for is those 561 MiB. `fold.js`
called `releaseResidentWeights(device, "w.")` at trunk-done so the pairformer's
weights would not sit beside the sampler's 378 MiB, which is right on a phone
and a pure loss on a card with tens of gigabytes. It is now the
`keepTrunkWeights` prior, null by default and true under `ampere`, with
`--keep-weights=off` as the control arm.

| 68 tokens | shipped | `keepTrunkWeights` | |
|---|---:|---:|---:|
| one step | 1.294 s | **0.663** | **1.95x** |
| 200 steps | 4.505 | **3.841** | **1.17x** |
| peak | 490 MiB | 869 | +379 |
| pLDDT / pTM | 84.208873 / 0.726961 | **identical** | |

🔴 **AND IT IS WORTH ALMOST NOTHING AT 256 TOKENS - 11.161 -> 11.028 s, 1.2%.**
The upload is the same 561 MiB at both sizes, because weights do not scale with
tokens; what changes is that at 256 there is enough compute to hide the
transfer behind and at 68 there is not. So this is a small-protein
optimisation, which is where the fixed gap was 27.5x and where a browser
actually works. The +379 MiB is constant too (777 -> 1157 MiB at 256), which is
why the prior is per-device: a 1365 MiB phone budget cannot pay it, and
`GpuMemoryBudgetError` already falls back by releasing residency and retrying.

🔴 **AND MOST OF THE WIN IS NOT THE BUS, SO IT SHOULD CARRY TO AN M2 - BUT IT
IS NOT SET THERE.** The two arms, profiled:

| 68 tokens, one step | keep=off | keep=on |
|---|---:|---:|
| wall | 1302 ms | **697** |
| `writeBuffer` host time | 169 | 48 |
| `writeBuffer` calls | 1341 | **397** |
| `writeBuffer` bytes | 561.4 MiB | 325.0 |

Only **121 of the 605 ms** saved was inside the `writeBuffer` call. And 236 MiB

so the transfer is a few percent of it at most. What is left is per-call driver

## Why the denoiser cannot be tiled out of this, and what is left

🔴 **AT 59 TOKENS THE TRANSFORMER HAS 45,312 OUTPUT ELEMENTS AND THIS DEVICE
HOLDS 221,184 THREADS.** `qkvg` dispatches `ceil(tokens/tile)` by
`qkvgSplits`, and `splitFor` is `width / lanes` - so the total thread count is
`tokens/tile x width` = 59 x 768, **whatever `lanes`, `splits` or `tile` are
set to**. Rearranging them moves the same threads into different workgroups.
Measured, not deduced: at tile 1, `--splits` 1/2/4/8/16 all read 25 ms at 59
tokens and 62-63 at 200.

🔴 **AND IT IS NOT WEIGHT TRAFFIC EITHER.** Doubling the weight bytes
(`--weights=f32`) costs **8%** - 24 -> 26 ms at 59 tokens, 62 -> 67 at 200. Nor
launches: 168 passes at this device's 8.4 us is 1.4 ms of a 25 ms step. The
kernel is simply too small to fill the machine, and the only cures are MORE
INDEPENDENT WORK (batching samples, or a longer protein) or splitting the
REDUCTION - a split-K form, which is new kernels rather than a knob.

🔴 **BUT THE CHEAPEST CURE IS FEWER CALLS, AND IT IS ALREADY WRITTEN.**
`flowOnGpu` walks the schedule deterministically in a handful of calls instead
of 200 stochastic steps, and `src/af3/diffusion-sampler-webgpu.js` records it
against crystals: 6MRR flow-8 **0.69 A / TM 0.951** against the 200-step
sampler's 0.66 / 0.953. On this A100, same sequence, same trunk:

| | trunk | diffusion | total | mean pLDDT | pTM |
|---|---:|---:|---:|---:|---:|
| `--mode=diffusion --steps=200` | 1.1 s | 8.5 s | **9.6 s** | 74.6 | 0.497 |
| `--mode=flow --steps=16` | 1.1 | 1.3 | **2.4 s** | **74.6** | 0.484 |
| `--mode=flow --steps=8` | 1.1 | 1.1 | **2.2 s** | 74.0 | 0.474 |

**4x on a whole fold for a flag**, with mean pLDDT identical at 16 cycles. It
is not free - pTM moves 0.497 -> 0.484, and the flow's spread across seeds is
narrower by construction, so it is a worse ENSEMBLE even where it is an equal
structure. And it is available to the JAX code too; AF3's `steps` is a config
field. What it is not is a WebGPU-specific trick, and what it does mean is that
the 4.6x gap on totals is dwarfed by a factor nobody was arguing about.

🔴 **AND AT FLOW SPEEDS THE FIXED COSTS ARE SUDDENLY THE TARGET.** Eight
denoiser calls at ~43 ms should be 0.34 s and the diffusion stage measures
**1.1**, so about 0.75 s of it is setup - the diffusion transformer's resident

## The trunk's shortest dispatch, which is actual code

🔴 **THE TRANSITION KERNEL DISPATCHES ROWS AND NOTHING ELSE.** `main` takes
`base_row = (group.x + group.y * GRID_WIDTH) * TILE` and that is the entire
grid - there is no second axis. So its thread count is
`ceil(rows / tile) * WORKGROUP`, full stop. The AF3 trunk's SINGLE transition
has `n` rows where the pair track has `n^2`: at 200 tokens that is 200
workgroups of the default 128 threads, **25,600 on a device that holds
221,184**. `bench-trunk.js --profile --tokens=200` put it at **54.87 ms, 13.6%
of the trunk's GPU time**, for 0.47 GFLOP - **2.3% of this device's arithmetic
ceiling**, against `pair-transition`'s 48% on the same kernel.

them; widening halves that block and buys back the `act[]` reads it was saving.
`project_out` has no such blocking - a plain strided loop - and it is the one
that moved. **Ask what a kernel already does per lane before widening it**,
which is the same question as docs/PERF.md's "ask what a kernel already fuses
before pricing its arithmetic".

🔴 **AND `single.attend` NEVER HAD THE DISEASE.** 3200 workgroups at 200
tokens, 204,800 threads, 93% occupancy. Its 2.2% of ceiling is that the pass
has 0.06 GFLOP to do - it is small, not starved. Low efficiency and low
occupancy are different diagnoses and only the second one this section is
about.

## The diffusion attention, and two wrong diagnoses before the right one

The largest pass in a denoiser step, at 2.5% of the arithmetic ceiling. It owns
one (token, head) a workgroup: 3840 workgroups of 256 lanes at 240 tokens,
983,040 threads where the device holds 221,184. **Oversubscribed, not starved**
- so whatever was wrong, it was not occupancy, and the two obvious candidates
were both nearly nothing:

| | |
|---|---|
| the idle lanes | its last phase is `for (d = local; d < DIMENSION; ...)` and DIMENSION is 48, so 208 of 256 lanes sit at the barrier. 64, 128 and 256 lanes measure the SAME; only 32 differs, and is worse. **Nothing.** |
| the barriers | two `stride = lanes/2` reduction trees are 16 of about 20. `subgroupMax`/`subgroupAdd` remove them: **5%.** |
| **the access pattern** | the logit loop gave a lane a whole KEY - DIMENSION contiguous floats, WIDTH*4 bytes between lanes, so a warp issued 32 separate 192-byte reads over 98 KB. Staging the chunk with a (key, channel)-indexed loop makes the global read coalesced: **1.30x.** |

Together `attend` goes **9.32 -> 6.38 ms at 240 tokens and 24.19 -> 16.43 at
400, 1.46x each**. Low efficiency, low occupancy and a bad access pattern are
three different diagnoses and only the third was this kernel's.

🔴 **AND THE SAME STAGING IS A LOSS IN THE ATOM ATTENTION, FIFTY LINES AWAY.**
`attendFor` in src/af3/atom-encoder-webgpu.js has the identical read -
`k[key_index * WIDTH + head * DIMENSION + d]`, one key a lane - and staging it
measures **1.65 -> 2.62 ms**, a 1.6x LOSS. Its DIMENSION is small, so a lane's
contiguous run is a few tens of bytes rather than 192, and the coalescing there
is not broken enough to pay for the copy and the barrier. **The fix is not "the
read is strided", it is "the strided read wastes whole sectors".** Check the
run length before porting it.

🔴 **AND grid.attend WILL NOT TAKE REGISTER BLOCKING HERE EITHER.** docs/PERF.md
prices that kernel per lane-key at ~160 scalar operations and 64 workgroup
reads; against an M2's ceilings those are 1.26 apart and against this device's
they are 2.6, so it reads as read-bound here and Q queries a lane divides the
read term by Q. Measured: Q=2 is **71.89 ms against 68.53** and Q=4 is 78.81.
Less catastrophic than the M2's 0.57x and 0.40x, and still a loss. A ratio of
ceilings predicted a win and the machine said no.

🔴 **AND THE ATOM DECODER'S OUTPUT TILE IS ALREADY RIGHT, WHICH IS THE THIRD
OCCUPANCY CONSTANT CHECKED AND THE FIRST THAT NEEDED NOTHING.**
`outputRowTileFor` picks the largest tile in 8/4/2 that leaves at least **256
workgroups** - another ten-core number, and the same shape as
`singleProjectSplits`'s 110 and the transition's 128-wide workgroup. Raising
the target to 600 (tile 2) or past 992 (tile 1) measures, twice each:

    target 256 - shipped   output-* 4.77, 4.77 ms   step 46.49, 46.47
    target 600             output-* 4.75, 4.71      step 46.12, 46.44

Nothing. The pattern that generated three wins does not generate a fourth here,
and the reason is worth keeping: this kernel's tile trades weight traffic
against workgroups and it is already at the balance, where the transition's
dispatch had NO second axis at all and the single track simply could not fill
the machine at any tile.

It is answerable directly: run the best generic GEMM in this tree at the exact

## Scan over steps, and moving the Gaussians to the GPU

🔴 **SCAN IS CAPPED AT 6.6% HERE, AND THE MEASUREMENT SAYS SO BEFORE ANY CODE
IS WRITTEN.** What `lax.scan` buys JAX is a loop with no host in it. This
sampler already has almost none: `profileDevice`'s summary puts the GPU at
**96% busy inside a step**, and `probe-sampler-overhead.js` at 240 tokens puts
the whole non-GPU cost at **3.2 ms of a 48.7 ms step** - augment 0.2, inject
2.1, euler 0.1, and 0.5 inside `head.run` that is not a labelled pass. Over 200
steps that is 640 ms of 9.7 s. There is no 3x hiding between the steps; there
never was, because the GPU was never waiting.

(A fold measures 54 ms a step rather than 48.7. The difference is
`tools/gpu/fold.js`'s own trajectory recording, which calls `Array.from` on a
17,280-element Float32Array twice a frame to build BOXED JavaScript arrays. It
is the tool, not the model - and worth knowing before quoting a fold's
per-step number as the library's.)

🔴 **AND THE GAUSSIANS CAN MOVE, AND THEY KEEP THE STREAM.** `inject` is 2.1 ms
of that 3.2, and it is the thing that stops the positions living on the device
across a schedule: `normalFrom` is Box-Muller over a 32-bit LCG, walked
serially on the host. A lane cannot walk a serial stream - but an LCG jumps
ahead in closed form, `state_n = A(n)*s0 + C(n)`, with A and C built by the
standard doubling in about 32 u32 multiplies. `probe-gpu-gaussian.js` is that
kernel:

| | ms for 17,280 draws | worst difference from the host stream | mean / sigma |
|---|---:|---:|---|
| host, today | 1.50 | - | - |
| **GPU, jumped LCG** | **0.20** (7.5x) | **6.45e-6** | 0.0038 / 1.0035 |
| GPU, counter hash | 0.30 | 6.93 - a different stream | 0.0026 / 1.0018 |

**6.45e-6** is f32 rounding of `log` and `cos` against JavaScript's f64, on
values whose sigma is 1. So this is not a new seed-to-structure mapping, which
is what a counter-based RNG would be; it is the same draws to about seven
digits. Early in the schedule sigma reaches 2273, so the worst perturbation to
a coordinate is about 0.015 A - against a seed-to-seed spread this repository
records at 0.93-1.12 A on 1QYS.

🔴 **SO THE SHAPE OF THE WORK IS CLEAR AND THE SIZE OF IT IS 6.6%.** Positions
resident on the device; augment, inject and the Euler step as three elementwise
kernels; the jumped-LCG generator above; and then as many steps as one likes in
one command buffer. It is a real refactor of the sampler and the head's input
path for two thirds of a tenth, and it should be weighed against the batch
dimension - which is 3x, touches the same four modules, and would use the same
device-resident positions when it got there. **Do them together or do the
batch one first.**

## WebGL2 reaches 48% of this device, through the vertex shader

🔴 **THIS SECTION HAS NOW BEEN WRONG THREE TIMES, EACH TIME BY STOPPING TOO
EARLY.** It said **165x slower** from jax-js's WebGL backend, which its authors
offer "on a best-effort basis" and which is a fact about one implementation.
Then **4x**, from a naive fragment GEMM. Then **3.3x**, from a properly blocked
one, with a tidy proof that 21.3 flops a fetch was "the ceiling of the API".
The proof was sound and the premise was wrong: it is the ceiling of the
FRAGMENT path. The answer is **1.5x**.

| | TFLOP/s | of 18.1 |
|---|---:|---:|
| LocalFold, WebGPU compute | 13.22 | 73% |
| **WebGL2, transform feedback** | **8.64** | **47.8%** |
| jax-js, WebGPU | 4.29 | 23.7% |
| WebGL2, fragment + MRT | 3.99 | 22.0% |
| WebGL2, naive fragment | 1.01 | 5.6% |
| jax-js, WebGL | 0.08 | 0.4% |

**8.64 against 3.99 - the vertex path is 2.2x the fragment path**, and the
whole difference is output budget. A fragment writes `MAX_DRAW_BUFFERS` x RGBA
= 32 floats; a vertex shader with rasterisation discarded writes up to
`MAX_VERTEX_OUTPUT_COMPONENTS`, and more outputs an invocation is more
arithmetic per fetch. This is the vertex shader used as a compute kernel, which
is what people did before compute shaders existed, and on this card it is worth
more than doubling.

🔴 **AND THE ADVERTISED LIMIT IS NOT THE REAL ONE.**
`MAX_TRANSFORM_FEEDBACK_INTERLEAVED_COMPONENTS` reads **128**, but the varyings
must also pack into `MAX_VERTEX_OUTPUT_COMPONENTS`, which is **124** - so 32
vec4 fails to link with "Could not pack varying v30" and 31 is the ceiling. The
best geometry that also divides 2048 is then 8 rows x 2 groups at intensity
32.0, and 8x1 in f16 beats it anyway at 8.64, so past about 21 flops a fetch
this path stops being fetch-bound and the model that predicted the fragment
numbers to 1% no longer applies.

Against LocalFold's hand-tuned WebGPU compute kernel that is **1.53x**, not
3.3x and nothing like 165x. It is still the wrong direction for this
repository - no compute shaders, no storage buffers, no f16 arithmetic, no
subgroups, no cooperative matrix, and above all no workgroup shared memory,
which is what `grid.attend`, the transition and the diffusion attention all
depend on. But "WebGL2 cannot do this work" was never true, and each time this
file said how far off it was, the number was wrong by measuring the easier
thing.

🔴 **AND ON THE SHAPES THIS REPOSITORY ACTUALLY RUNS IT IS 1.6x TO 2.1x, NOT
1.5x - AND ONE OF THEM DOES NOT FIT AT ALL.** A square matmul is the number
everyone quotes and none of the trunk's kernels have:

| shape | WebGL2 TF | LocalFold WebGPU | |
|---|---:|---:|---:|
| square 2048^3 | 8.54 (47%) | 13.22 (73%) | 1.55x |
| **AF2 transition**, 30208x256x1024 | **9.05 (50%)** | 14.70 (81%) | 1.62x |
| diffusion `qkvg`, 240x768x768 | 1.51 (8%) | 3.18 (18%) | 2.1x |
| **AF3 pair-transition**, 40000x128x512 | **cannot be expressed** | 8.63 | - |

🔴 **AND THAT LAST ROW IS THE REAL VERDICT.** `MAX_TEXTURE_SIZE` is 32,768 and
the AF3 pair track has `tokens^2` rows, so the operand stops fitting a texture
axis at **181 tokens**:

    128 tokens ->  16,384 pair rows   fits
    181        ->  32,761            fits
    200        ->  40,000            does not
    400        -> 160,000            does not

Every pair-track kernel would need its row index tiled across two texture
dimensions, with the address arithmetic that implies, for every fold longer
than a small domain. WebGPU has no such limit: `maxStorageBufferBindingSize` is
2 GB here and a buffer is one-dimensional.

🔴 **AND THE LAST 2x IS ONE LINE: WHICH INDEX VARIES FASTEST.** Neighbouring
invocations share whichever index is the SLOW one, so that operand's fetches
are uniform across them and are served once. At 8 rows x 1 group the kernel
reads **8 A texels and 4 B texels** an iteration, so A is the one worth making
uniform - which means `nGroup` fastest and `mBlock` slowest. Swapping the two
lines:

| | TFLOP/s | of 18.1 |
|---|---:|---:|
| `nGroup` fastest - A broadcasts | **8.54** | **47.2%** |
| `mBlock` fastest - B broadcasts | 4.10 | 22.7% |

**2.08x for choosing which of two divisions to write first**, and it is the
whole difference between "WebGL2 gets 22%" and "WebGL2 gets 47%". The geometry
sweep is a genuine optimum around 8x1 and falls off both ways - 2x1 5.77, 4x1
7.99, **8x1 8.59**, 16x1 7.23, 8x2 7.94 - because past there the accumulators
cost more occupancy than the intensity buys. Note that 8x2 has HIGHER intensity
(32.0 against 21.3) and is slower, so unlike the fragment path this one is not
fetch-bound; the model that predicted the fragment numbers to 1% stops
applying.

🔴 **THREE MEASUREMENT TRAPS, ALL OF WHICH REPORTED A CONFIDENT WRONG NUMBER.**
`gl.finish()` does not block here - four draws of a 2048-cube measured **0 ms**
until `readPixels` replaced it. A buffer bound to `TRANSFORM_FEEDBACK_BUFFER`
may not also be bound to `ARRAY_BUFFER`: `getBufferSubData` then returns zeros
behind an `INVALID_OPERATION` nobody reads, and both the base and the transform
feedback OBJECT have to be released - `tools/gpu/probe-webgl2-tf.js` is the
smallest case that works. And the surgery arms that price a fetch by replacing
an operand with `vec4(1.0)` are useless here, because with a = 1 the eight
accumulators become one expression and collapse: that arm reported 250
TFLOP/s.

### What they issue at

`tools/gpu/probe-matrix-ceiling.js` is `probe-alu.js`'s question for the matrix

Two things matter more than the headline:

- **f32 accumulation is free.** 309.7 against 310.9. The units accumulate in

- **Eight accumulators saturate it.** 308.6 at 8, 310.8 at 16, 310.9 at 32 -

🔴 **AND THAT 1.24x IS A CEILING, NOT A SPEEDUP.** The arm computes `z @ W`;

read of z, and emits the gated product. Replacing it means a GEMM writing the

Note also 14.9 TFLOP/s here against 28.2 on AF2's transition. The difference is
K: `cZ` is 128 where a transition's inner extent is 256 or 1024. A staged panel
amortises over K, so the matrix path wants a deep inner dimension as much as it
wants rows - which is the third condition, after "materialised" and "big".

So the rule this work arrives at, for whoever looks next: **the matrix units
pay where an operand is already materialised, the problem is past a billion
multiply-accumulates, and K is deep.** AF2's transition is all three. AF3's
diffusion fails the second, and its pair track fails the first.

### Three bugs this found, and where each was caught

🔴 **THE KERNEL NEVER READ `weight_offset`.** It indexed the weight buffer from
zero. Both the bench and `check-staged-matrix.js` set that field to zero, so
both passed a kernel that ignored it; AF2's differential checker caught it at
**relRMS 1.85**, after the kernel had already been called correct and
committed. The checker now packs its weights at a nonzero base - 4 and 3, so
that one arm is aligned and exercises the vec4 path and the other is not and
exercises the scalar fallback.

🔴 **AND `weight_offset` IS A RUNTIME VALUE THE VEC4 PATH CANNOT ASSUME.** A
vec4 read at element `i` returns the quad containing `i`, so an unaligned base
shifts the whole weight panel - wrong, not slow. The shader does not know the
offset and the caller does, so `createTransitionShaders` asks per pass: a
transition's two projections sit at different offsets in one packed buffer, and
either may be the unaligned one.

🔴 **AND THE GATE WAS BELOW THE BRANCH IT NEEDED TO BE ABOVE.** Placed after
`requested === "f16"`, which returns, the matrix path was unreachable for every
caller naming f16 - which is the differential checker. It ran green while
testing none of this. The matrix path IS the f16 path where the units exist, so
the gate is `requested !== "f32"`.

🔴 **THE MULTIMER BLOCK IS CHANGED AND UNVERIFIED HERE.** `src/multimer/block.js`
takes the same three edits and `npm test` passes, but this box has only the
monomer weights, so `fold-af2.js --family=multimer` cannot run. It needs a fold
on a machine that has them before it is trusted.

## The diffusion, pushed: split-K is the missing half of the token tile

🔴 **THE PREMISE OF THIS SECTION IS WRONG AND THE MEASUREMENTS IN IT ARE NOT.**
It opened "the gap to JAX is the diffusion - 33x against the trunk's 12x, like
for like - so this is where the work went", and that 33x came from dividing
JAX's MARGINAL EXTRA SAMPLE by 200 steps. Samples are a `vmap` axis, not extra
trajectories; see "AF3 against AF3" above. Measured by sweeping `--steps`, the
denoiser step is **2.0x**, the closest of anything on this page, and 90% of a
LocalFold fold is not a compute pass at all. Everything below still happened and
every number in it still holds - the kernels really did get 1.7x faster - but it
was the tenth of the fold that was already nearest parity. Read it as a record
of the kernel work, not as a ranking of what to do next.

Five hypotheses, four of them wrong, and the fifth is worth building.

**What a denoiser step costs, GPU-only, by size:**

| tokens | 68 | 128 | 240 | 384 |
|---|---:|---:|---:|---:|
| step | 29.40 ms | 32.93 | 46.68 | 69.51 |
| passes | 211 | 211 | 217 | 228 |

The marginal cost per token RISES with size (0.059, 0.123, 0.159 ms) because
attention is quadratic, so extrapolating the low end back puts **~25 of the
29.4 ms at 68 tokens in a size-independent floor** - 86% of a step. That floor
is the target, and it is not what it looks like.

🔴 **IT IS NOT DISPATCH OVERHEAD.** `probe-dispatch.js` measures 6.2 us for a
dispatch in one pass. The transformer's 144 dispatches are 0.9 ms of a 29.4 ms
step - 3.5%. (And `encoder-each` is 42 us, seven times `pass-each`, which is
worth knowing separately: the encoder is the expensive object, not the pass.)

🔴 **IT IS NOT HOST OVERHEAD EITHER**, which the scan section above already
established at a 6.6% cap, and `idleShare` confirms at 4-6% here.

🔴 **IT IS NOT WEIGHT PRECISION.** The denoiser ALREADY reads f16 weights -
`diffusion-transformer-webgpu.js:1242` defaults to f16 where line 244's
shader-level fallback says f32, and only the shader builder sees the latter.
Forcing f32 costs 7% (qkvg 180.8 -> 194.6 us), which is both the value of the
f16 path here and the proof that weight bytes are not the binding constraint.

🔴 **AND IT IS NOT PLAIN UNDERFILL, WHICH IS THE ONE WORTH DWELLING ON.** The
projections give one thread per output channel per token: at 68 tokens and a
width of 768 that is 52,224 threads against ~221,000 slots, 24%. So splitting
the inner extent to multiply the thread count is the obvious move, and on its
own **it loses**: at one output a lane, 16x the threads measures 0.86x. The
kernel is not short of threads.

### What it actually is: 0.5 flops per byte

The inner loop is one multiply-add per weight loaded. `qkvg` reads four weights
- q, k, v and the gate - and does four multiply-adds, which is 8 flops for 16
bytes: **0.5 flop/byte**, capping it near 2.5 TFLOP/s off an L2 that gives about
5 TB/s. It measures 1.97. There is no headroom to find; the ratio has to change.

The token tile changes it - a workgroup holding T tokens loads each weight once
and uses it T times, so intensity is T/2 - and it costs workgroups, ceil(68/T)
instead of 68. Those two effects cancel, which is why the shipped kernel pins
the tile to 1 below 175 tokens and why forcing it higher makes things worse:

| shipped kernel, 68 tokens | tile 1 | tile 2 | tile 4 |
|---|---:|---:|---:|
| step | **29.40 ms** | 32.77 | 40.75 |
| qkvg | **180.8 us** | 266.2 | 345.8 |

and it is not a precision effect - with f32 weights the tile costs the same
0.71x. At 240 tokens, where halving the workgroups still leaves plenty,
`ffw-wide` DOES take 1.64x from tile 2 and `qkvg` takes 4%; the difference
between those two is that qkvg carries four accumulators a lane and ffw-wide
two, and this file already records a spill at that pressure.

### The two levers fail for opposite reasons, so use both

`probe-split-k.js` models `qkvg` exactly - 68 x 768 -> 768, four outputs a lane
- and every arm is checked against a known answer, because a kernel that
computes nothing is the fastest kernel there is:

| | workgroups | TFLOP/s | |
|---|---:|---:|---:|
| plain, as shipped | 204 | 1.97 | 1x |
| split K by 8 | 1632 | 2.63 | 1.34x |
| token tile 4 | 51 | 2.18 | 1.10x |
| **tile 4 + K split 8** | 408 | **4.54** | **2.30x** |

**Neither lever passes 1.35x alone and together they reach 2.30x**, because the
tile buys intensity and pays in workgroups and the K split buys workgroups and
pays in partial traffic. Tile 4 with K split 8 has tile 4's arithmetic and
twice the plain kernel's occupancy.

🔴 **AND THE BALANCE INVERTS WITH SIZE, so this needs a gate and not a
constant.** Tile 4 alone: 1.10x at 68 tokens, **2.01x at 240**, **2.91x at 384**.
Tile 4 + K/8: 2.30x at 68, 1.68x at 240, 2.01x at 384. Past a few hundred
tokens the tile no longer starves the device and the split is pure cost - which
is the same shape of rule `chooseMatrixLinear` needed, and for the same reason.

**So the proposal is: split K in the diffusion transformer's projections, gated
to small token counts, and raise the token tile behind it.** Built, for the two
projections it fits - see the next section.

🔴 **AND IT IS NOT WHAT THE MATRIX UNITS DO.** Measured above: at the diffusion
transformer's shape the staged matrix kernel reaches 1.88 TFLOP/s against the
shipped fused kernel's 3.9. Tensor cores do not help a kernel bound at 0.5
flop/byte; raising the ratio is the only thing that does, and split-K plus the
tile is how.

## ffw-out, where the epilogue is a second projection

`ffw-out` was the largest pass left, 3.17 of a 19.98 ms step. It is
K-splittable and I had written it off earlier for a reason that turned out to
be backwards: after its K loop it computes a SECOND projection - the zero-init
gate over 384 conditioning channels - then a sigmoid and a residual add, about
a third of the kernel. I assumed that had to be paid again per part.

🔴 **IT DOES NOT: THE EPILOGUE IS LOOP-INVARIANT ACROSS THE SPLIT.** Nothing in
it depends on which slice of K a part walked, so it moves into the reduction
and runs exactly once. Only the K loop divides.

| | before | after |
|---|---:|---:|
| `ffw-out` | 3.16 ms | **1.44** |
| `ffw-out-reduce` | - | 1.07 |
| **together** | **3.16** | **2.51** (1.26x) |

Parts swept: 1 gives 3.16, 2 gives 2.64, 4 gives 2.51. The epilogue's 1.07 ms
is a floor the split cannot touch - it is 1.8 TFLOP/s of its own projection,
the same weight-bound shape as everything else here, and splitting THAT is the
next layer.

🔴 **AND THE PART COUNT IS NOT FREE TO CHOOSE: THE CHUNK MUST DIVIDE THE SPAN.**
A part walks its slice in chunks of `outChunk`, so with an intermediate of 1536
and a chunk of 384 the only legal counts are 1, 2 and 4. At 8 the span is 192
and `chunk0 < start + 192` still runs one whole 384-wide iteration, reading the
NEXT part's slice and double-counting it - a silent wrong answer. The shader
factory throws on it and the caller falls back.

### attention-output takes the same split and it is a WASH

The same recipe, and it works exactly as designed - **the projection goes 2.11
-> 1.00 ms, 2.11x** - and the kernel as a whole does not move:

| | fused | split |
|---|---:|---:|
| `attention-output` | 2.11 ms | 1.00 |
| `attention-output-reduce` | - | 1.09 |
| **together** | **2.11** | **2.09** |

The epilogue is the same zero-init gate as ffw-out's and costs the same ~1.08
ms, but it is **52% of this kernel where it is 34% of ffw-out's** - so there is
nothing left for a 2x on the other half to buy. Correct (fold gate exact with
it on), measured, and **defaulted off**: `attnSplits: 1`. The mechanism stays
because it cost nothing to keep and the number is worth not re-deriving.

🔴 **AND THE FIRST VERSION WAS A 0.57x LOSS FOR A REASON WORTH CARRYING.** This
kernel's staging - `gathered * logistic(gate)` over the whole width - sits
OUTSIDE its projection loop, where ffw-out's sits inside the chunk loop. Split
naively, every part repeated the whole gate: 2.11 -> 3.67 ms. A part has to
stage only its own slice, which also shrinks its workgroup array from the width
to the span. **Where the staging sits relative to the loop decides whether a K
split is free or quadratic.**

### Three mistakes, all mechanical, all caught by the run

- **the split store landed in the wrong kernel.** `attention-output` carries
  the same zero-init-gate comment I anchored on, and a `replace(..., 1)` takes
  the first match. It compiled and failed at `mode is not defined`.
- **a `return` is not enough to drop an epilogue.** With binding 3 rebound to
  the partials, the epilogue's `act` is unresolved - and WGSL rejects an
  unresolved name in dead code as readily as in live code. The epilogue has to
  be omitted from the source, not skipped at runtime.
- **and an unused binding is dropped from an `auto` layout.** A split part never
  touches `cond`, so binding 1 vanished and the positional bind group failed to
  match. The split shader declares three bindings, contiguously.

Also: `outKSplits` was resolved before `outChunk` existed and read it in its
temporal dead zone, which failed every run that asked for a split and none that
did not - so the arm that worked was the arm doing nothing.

## The epilogue floor, removed: hoist the gate and batch it over the blocks

Two sections up, ffw-out's split left "a floor the split cannot touch" and named
splitting the epilogue itself as the next layer. The next layer is not a split.

🔴 **THE EPILOGUE IS NOT PART OF THE BLOCK CHAIN AT ALL.** Both gates are
`bias + cond @ W_zero`, and the conditioning does not move with the block -
`condBuffer` is bound unchanged to all twenty-four. Nothing in the epilogue
reads the block's activation. It sat inside the block loop only because that is
where its weights are, which is a fact about the weight layout and not about the
computation.

So `packZeroGateWeights` concatenates those weights across the blocks and one
dispatch takes **the block as its z axis**. At 68 tokens that is 17 x 3 x 24 =
**1224 workgroups once**, where the epilogue ran **204, twenty-four times**.

Measured with `fold.js --profile --profile-from=trunk-done` at 68 tokens, both
arms truncating at the same 144 passes so the rows compare:

| pass | fused | batched |
|---|---:|---:|
| `attention-output` | 13 ms | **8** |
| `ffw-out-reduce` | 7 | **2** |
| `zero-gates` (x6, both gates, all 24 blocks) | - | 3 |
| **together** | **20** | **13** |

**1.17 ms a step of a ~17.4 ms call.** One dispatch stages the conditioning once
and each `d` serves two weight reads, which is exactly the traffic the two
epilogues were each making alone.

🔴 **AND IT IS BIT-EXACT, WHICH IS THE POINT AND NOT A BONUS.** The arithmetic is
unchanged and so is its ORDER - seeded with the bias, then accumulating
`cond[d] * w[d]` over increasing d, in f32, from weights of the same precision.
A 20-step fold returns pLDDT 85.5743482503326 and pTM 0.7386928546954604 with
the knob on and off, to all sixteen digits. A hoist that only ALMOST reproduces
the answer would be a different model, and the tolerance table in
`tools/gpu/relative-rms.js` exists because that distinction has been lost here
before.

🔴 **IT IS ALSO PER TOKEN RATHER THAN PER ROW.** `perToken` reduces a row to
`row % TOKENS` for the conditioning, so under a batched sampler the old epilogue
recomputed an identical gate for every sample. The batched buffer is
`blocks x tokens x C`, 5.0 MB at 68 tokens.

🔴 **AND THE REDUCE LOST A BINDING, WHICH FAILED THE FIRST RUN.** The gate was
`ffw-out-reduce`'s ONLY read of `weights`. Precomputed, that binding goes unread
and `layout:"auto"` DROPS it - so a positional bind group of four failed with
*"binding index 2 not present in the bind group layout"*. The split form of the
same kernel carries a comment warning of exactly this, written when it was first
earned. This was the second time; the dispatch now picks its binding list by the
same flag the shader picks its declarations by.

Off by default at `diffusionBatchedGates: null`: it duplicates ~14 MB of f16
weights and needs the blocks resident, which is the trade the budget fallback
exists to refuse.

### And then all six of them, because adaln is the same shape

`adaln` and `ffw-adaln` compute their scale and shift the same way: a
`C_COND x C` projection of a conditioning that does not move with the block.
Only their last line reads the activation. So six projections were sitting
inside the block loop for the same non-reason, and the four kernels holding them
were **the four most underfilled passes in a denoiser call** - `attention-output`
2.13 ms, `adaln` 1.36, `ffw-adaln` 1.33, `ffw-out-reduce` 1.07, every one of them
at 204 workgroups a pass.

All six batch now. What is left of a conditioned norm is the activation's own
LayerNorm and an elementwise apply, which is what those kernels always were
underneath.

| per denoiser step, 68 tokens | fused | batched |
|---|---:|---:|
| the four kernels | 7.50 ms | 4.14 |
| `zero-gates`, all six projections, all 24 blocks | - | 0.71 |
| **together** | **7.50** | **4.85** |

Paired folds at 200 steps, order alternating: **6/6 favour, median 1.1450,
-0.451 s of 3.59, t=33.4**, pLDDT 84.208873 in all twelve. A 68-token 200-step
fold is **3.135 s, from 3.700**.

🔴 **THE LAYER-NORM SCALE CANNOT BE FOLDED INTO THE PROJECTION WEIGHT.** It is
the obvious optimisation - `cond[d] * lnScale[d] * ws[d][c]` regrouped so the
constant folds at pack time - and it rounds differently, which forfeits
bit-exactness for nothing measurable. The kernel stages `cond_norm` per block
and projects it, exactly as the kernel it replaced did.

🔴 **AND THE TWO CONDITIONINGS ARE NOT INTERCHANGEABLE, WHICH COST A WRONG FOLD.**
The zero gates read the RAW conditioning; the conditioned norms read the
NORMALISED one that `cond-norm` produced. `attention-output`'s own comment says
so in capitals, and I still bound `condBuffer` to both. It compiles, it runs, and
it folds a different protein: **pLDDT 64.29 against 85.57**. The kernel takes
both buffers now.

### What was checked, beyond pLDDT

pLDDT is one scalar, and a hoist that claims bit-exactness should be held to the
instrument that measures it:

| | |
|---|---|
| raw transformer output, batched vs not, interleaved | **relRMS 0**, and the call 11.5 -> 8.1 ms, **1.405x** |
| a 256-token fold, both arms | pLDDT 80.7964703093644, identical |
| `check-difftx-samples.js` | identical across 4 arms, 15 shaders |
| `check-difftx-batched.js` | `againstOneSample [0, 0]`, `betweenSamples [0]`, ok |

🔴 **AND HERE EXACTLY ZERO IS THE RIGHT ANSWER, WHERE USUALLY IT IS THE TELL.**
`tools/gpu/relative-rms.js` warns that a K split reads ~1e-7 and never 0.0
exactly, because regrouping a sum changes its rounding - a perfect score there
means the instrument is comparing nothing, which is how 106 arms once passed
vacuously. This hoist MOVES arithmetic without reordering it: same sequence over
d, same f32 accumulator, same weight precision. So 0 is what it should read, and
`correct: true` from the guarded helper is what says real arrays were compared.
The last check matters because the gate is stored per TOKEN and shared across
samples, which until then was a claim rather than a measurement.

### What it costs in memory

Linear in the token count, about **1.2 MB a token**, plus a fixed 85 MB of
duplicated f16 weights:

| tokens | gate buffers | scale/shift | total extra |
|---:|---:|---:|---:|
| 68 | 10 MB | 20 | **115 MB** |
| 256 | 38 | 75 | 198 |
| 384 | 57 | 113 | 255 |
| 768 | 113 | 226 | 425 |
| 1500 | 221 | 442 | 749 |

Nothing on a 40 GB card, and the knob is device-gated so a small device never
turns it on. Making the block weight buffers one contiguous allocation would
remove the 85 MB duplicate and is the larger refactor this deliberately avoided.

### The batched kernel is the one that wants a BIG tile

Every other kernel in this stack is starved of workgroups and wants a tile of 1;
the shipped rule pins it there below 175 tokens. This one has the block axis to
fill the device with, so what binds it is re-reading the same six weight slices
once per token group - **5.8 GB a step at a tile of 1, 0.76 at 8**. Swept at 68
tokens, every arm bit-identical:

| `gateTile` | 1 | 2 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|---:|
| `zero-gates` a step | 1.43 ms | 0.86 | **0.71** | **0.71** | 0.86 |

Default 8, clamped against `maxComputeWorkgroupStorageSize` in `#compile` where
the limits are: the staging is `gateTile * C_COND` floats, so 16 asks 24 KiB of a
16 KiB default and fails pipeline creation rather than running slowly.

🔴 **AND THE DISPATCH DIVIDED BY THE WRONG TILE, which is this file's oldest
trap.** The comment above `fits` records shaders tiling by four under a dispatch
dividing by eight, "every second tile of tokens simply never projected, reported
by the bench as a 30% speedup". Here the `zero-gates` dispatch divided by the
shared `tile` while the shader was built with `gateTile` - the benign direction,
68 groups launched where 9 do the work and the other 59 returning at the bounds
check, so the answer was right and only 7.5x the launches were wasted. Benign by
luck of a guard is not a reason to keep it.

🔴 **THREE KERNELS LOSE A BINDING ENTIRELY, AND AN AUTO LAYOUT DROPS IT.**
`ffw-out-reduce`, `adaln` and `attention-output-reduce` each read `weights` for
nothing but the hoisted projection, so a positional bind group of four fails
with *"binding index 2 not present in the bind group layout"*. The
`attention-output-reduce` one was latent - `attnSplits` is 1 by default, so
nothing had compiled that form until it was tested deliberately.

### What the hoist re-opened, and what it did not

The `attention-output` split was refused because the epilogue was "52% of this
kernel... nothing left for a 2x on the other half to buy". That epilogue is gone,
so the refusal's premise is gone. Re-measured, three rounds, baseline re-taken
each round:

| | mean of 3 | vs baseline |
|---|---:|---:|
| baseline | 3.1345 s | - |
| `attnSplits=2` | 3.1057 | +0.93% |
| `attnSplits=4` | 3.0998 | +1.12% |
| `normSplit=off` | 3.1280 | +0.21% |
| `gateTile=4` | 3.1328 | +0.05% |

🔴 **AND ~1% NON-MONOTONIC IS STILL NOT A RESULT.** `attnSplits` 2 beats 4 in
round three and loses to it in the other two, which is what this file has twice
called noise at this size. More to the point, the traffic arithmetic says a K
split CANNOT be the lever here: a split divides the work among parts, and every
part still re-reads the weight slice once per token group, so **the split moves
occupancy and leaves bandwidth exactly where it was**.

`normSplit=off` is now a wash either way, which is itself the finding: it used to
recompute the activation norm once per output split against a projection that
dominated the kernel, and the projection is hoisted. Left on, because nothing
argues for changing it.

### The tile, which is what the traffic says

At 68 tokens the two remaining large passes sit at their bandwidth floor, and it
is the TOKEN TILE that divides that traffic, not the split:

| pass | tile | token groups | weight traffic | floor | measured |
|---|---:|---:|---:|---:|---:|
| `attention-output` | 1 | 68 | 1.93 GB/step | 1.28 ms | **1.43** |
| `ffw-out` (+reduce) | 1 | 68 | 3.85 | 2.57 | **1.86** |
| `attention-output` | 4 | 17 | 0.48 | 0.32 | |
| `ffw-out` | 4 | 17 | 0.96 | 0.64 | |

The file already had the rule and had not applied it: *"splitting K and the token
tile are one decision... the split is what makes a bigger tile affordable"*, and
*"only qkvg has a K split behind it, so only qkvg can afford the bigger tile"*.

🔴 **BUT ffw-out HAS HAD A K SPLIT SINCE outKSplits LANDED, AND ITS TILE WAS
STILL CAPPED BY THE SHARED ONE.** `outTile` read
`Math.min(wantedTile, tile, fits(outChunk))`, and `tile` is 1 everywhere below
175 tokens on this device - so the `min` pinned it to 1 and **silently overrode
outTile's own sweep**, three comments above it, which had chosen four ("at 150
tokens 2 -> 138 ms, 4 -> 128, 8 -> 132"). A conclusion can be measured, written
down, and then cancelled by a later change to a different number.

`attention-output` now takes the same treatment through `attnOutTile`, built
under its own `tilingFor` the way qkvg and ffw-wide are.

Paired, five pairs, order alternating, against the previous behaviour
(`--attn-splits=1 --out-tile=1`):

| | |
|---|---|
| ratios | 1.0559 1.0628 1.0615 1.0649 1.0543 |
| median | **1.0615**, mean saving 0.178 s, t=31.8, 5/5 |

**A 68-token 200-step fold is 2.966 s, from 3.700 at the start of this work -
24.7%.** Against native JAX at matched settings (1.674 s) that is **1.77x, from
2.21x**.

🔴 **AND THE WIN IS SMALLER THAN THE TRAFFIC ARITHMETIC PREDICTS, which is worth
keeping rather than explaining away.** This card has **40 MB of L2** and
`attention-output`'s entire weight set is 24 x 768 x 768 x 2 = **28 MB**, so most
of the re-reading the tile removes was already being absorbed. The model's floor
of 1.28 ms at a tile of 1 matched the measured 1.43; its predicted 4x at a tile
of 4 did not arrive. A bandwidth model on this card has to be checked against
L2, not just against DRAM.

🔴 **AND BOTH TILES MUST BE RESOLVED AFTER THE SPLIT COUNTS THEY DEPEND ON.**
Placed beside the others they read `outKSplits` in its temporal dead zone and
every run died with *"Cannot access 'outKSplits' before initialization"* - the
same trap the note on `outChunk` records, in the same function, hit again.

## 256 tokens is a different regime, and the crossover was stale

68 tokens is 1.77x native JAX and 256 is 3.6x, so the scaling end is where the
gap lives. `fold.js --profile --profile-from=trunk-done` says why the tuning in
this file does not reach it - at 256 tokens **there is not a single reduce pass
in the profile**. `splitting` is `tokens < crossover` and the crossover is 175,
so `kSplits`, `outKSplits`, `attnKSplits` and every per-kernel tile that depends
on them disengage together.

Per denoiser step, the two sizes are barely the same model:

| | 68 tokens | 256 tokens |
|---|---:|---:|
| `attend` | 1.1 ms | **7.9** |
| `qkvg` | 1.2 | **7.0** |
| `ffw-wide` | 1.2 | 4.9 |
| `ffw-out` (+reduce) | 1.9 | 3.0 |
| `attention-output` | 1.4 | 1.8 |
| `adaln` + `ffw-adaln` | 0.9 | 1.2 |
| `zero-gates` | 0.7 | 1.9 |

🔴 **AND THE 175 NO LONGER HOLDS.** It was set from a measurement at 240 tokens -
*"the shipped rule disengages and the step is 46.63 ms against 46.68 before -
unchanged"* - which was true of the kernels as they were then, and is not true of
them now that the conditioning is hoisted and the tiles are per kernel. At 256
tokens, 200 steps, two rounds, every arm at pLDDT 80.3524697923889:

| | splits off | splits on |
|---|---:|---:|
| **hoist off** | 11.4147 s | 10.8688 (+5.0%) |
| **hoist on** | 11.1932 (+2.0%) | **10.4147 (+9.6%)** |

So the splits are worth **5%** at 256 and the hoist **2% on its own, 4.5% on top
of them** - and the crossover was throwing the first of those away. The hoist has
no crossover of its own and does not need one; it pays at both sizes.

### Where it actually is, by length

Swept with `--crossover=99999` against the shipped rule, 60 steps, two rounds a
point:

| tokens | splits off | splits on | |
|---:|---:|---:|---:|
| 272 | 4.9185 s | 4.6895 | **+4.9%** |
| 408 | 8.7013 | 8.5645 | **+1.6%** |
| 544 | 13.7658 | 13.7380 | +0.2% *(a wash)* |

The linear trend crosses zero at **~536 tokens**, so the rule is now
`crossover: 512` - above the last clearly-positive point and below the wash.

🔴 **AND IT DECAYS FOR A REASON THE ARITHMETIC GIVES, which is what makes the
new number more than a curve fit.** The split's partials are written once and
read once per block, so their traffic grows with the token count while what the
split buys - workgroups on a device that has enough of them by then - does not:

| tokens | partial traffic a step | at 1.5 TB/s |
|---:|---:|---:|
| 68 | 1.3 GB | 0.9 ms |
| 256 | 4.8 | 3.2 |
| 544 | 10.3 | 6.9 |

A crossover SHOULD exist. **175 was simply the wrong one**, by a factor of three.

🔴 **AND 136 TOKENS IS A DEGENERATE ROW, kept as the noise floor.** Below the old
175 both arms of that comparison are the same configuration, so the four runs
spanning **3.3%** measure nothing but this box's spread at 60 steps - which is
the number the +1.6% at 408 has to be read against.

🔴 **A CROSSOVER IS A MEASUREMENT WITH AN EXPIRY DATE.** This one was correct
when taken and became wrong when the kernels underneath it changed, silently,
because nothing re-runs it. `fold.js --crossover=N` exists now so it can be
re-asked; there was previously no way to ask.

### What `attend` responds to, so the next attempt starts from the map

Before rewriting the kernel on a third hypothesis, the knobs that already exist.
At 256 tokens, `attend`'s pass time, two rounds agreeing to the millisecond:

| | `attend` | |
|---|---:|---|
| baseline | **51 ms** | |
| `attendStageKeys=false` | 71 | **+39%** |
| `attendSubgroups=false` | 54 | +6% |
| `lanes=128` | 52 | a tie |
| `lanes=64` | 61 | +20% |

🔴 **STAGING IS THE ONE THAT MATTERS, AND IT IS ABOUT COALESCING, NOT BARRIERS.**
Unstaged, the key loop is `for j = local; j < TOKENS; j += lanes` with each lane
reading 48 consecutive floats of row j - so neighbouring lanes are **768 floats
apart**, and every read is a separate transaction. Staging loads `(key, channel)`
together, which is contiguous. That is the 39%.

🔴 **WHICH IS ALSO WHY "STAGE v TOO" IS NOT THE NEXT MOVE.** The value loop is
`for d = local; d < DIMENSION; d += lanes`, so for a fixed j the active lanes
read 48 CONSECUTIVE floats - already one coalesced transaction. v does not have
the problem k had, and staging it would buy a barrier and no bandwidth. (It
would also be free in shared memory, since `k_tile` is dead by then - so the
reason not to do it is the access pattern, not the budget.)

🔴 **AND NARROWER WORKGROUPS LOSE, WHICH THE SHARED MEMORY EXPLAINS.** A
workgroup holds ~14 KiB of `k_tile` and `logits` whatever its lane count, so an
SM fits eleven of them either way: at 256 lanes that is 2816 threads and at 64 it
is 704. Better per-workgroup lane utilisation (25% -> 100% on the key dots) is
bought by dropping SM occupancy to a third, and the occupancy wins.

### And the key chunk, which a 16 KiB assumption had capped

`keyChunk` is a hardcoded `?? 64` that no device could move, and it sizes
`k_tile`. It was chosen against a 16 KiB workgroup-storage limit; **this card
reports 49152**, so 192 keys fit where 64 were being staged. Made tunable
(`diffusionAttendKeyChunk`) and swept at 256 tokens, both rounds identical:

| `keyChunk` | `k_tile` | chunks | dot lanes | `attend` |
|---:|---:|---:|---:|---:|
| **64** | 12 KiB | 4 | 25% | **51 ms** |
| 96 | 18 | 3 | 38% | 51 |
| 128 | 24 | 2 | 50% | 56 |
| 192 | 36 | 2 | 75% | 67 |

Fewer barriers and four times the lane utilisation, and it is **31% slower**.

🔴 **FOUR MEASUREMENTS, ONE MECHANISM: `attend` IS BOUND BY SM RESIDENCY, AND
EVERYTHING THAT BUYS PER-WORKGROUP EFFICIENCY WITH SHARED MEMORY OR LANES
LOSES.**

| | what it buys | what it costs | |
|---|---|---|---:|
| `lanes=64` | dots 25% -> 100% | threads/SM 2816 -> 704 | +20% |
| `keyChunk=192` | 4 chunks -> 2, dots -> 75% | 11 workgroups/SM -> 4 | +31% |
| value split 5 ways | AV 19% -> 94% | a barrier and a shared round trip | +4% |
| `attendStageKeys=false` | 12 KiB back | coalescing | +39% |

The kernel already sits where those four trades balance, and the hardcoded 64
turns out to be right on this device - by accident of an assumption that was
wrong about the limit and right about the answer.

🔴 **AND THAT RETIRES THE QUERY-TILING IDEA THE SECTION ABOVE LEFT OPEN.** Four
queries a workgroup needs `logits` four times over - 4 KiB more shared memory -
to buy exactly the per-workgroup efficiency the four rows above each paid for
and lost. It is the same trade with the same sign, and it should be expected to
lose for the same reason. Not built, and now with a reason rather than an
absence of one.

### Tried and refused: making the sampler's Gaussians cheaper on the host

`probe-sampler-overhead.js` at 68 tokens, on tonight's build:

| | ms a step |
|---|---:|
| wall | 13.2 |
| GPU | 12.0 |
| `inject` | **0.8** |
| augment / euler / copies | 0.1 / 0.1 / 0 |

So the host is 1.2 ms of a 13.2 ms step and `inject` - the Box-Muller draw for
every atom - is two thirds of it, 5.4% of a 200-step fold. Three bit-exact ways
to make it cheaper, all measured, all flat:

| | |
|---|---|
| `Math.imul` for the LCG | bit-identical, and **51% SLOWER** - V8 already keeps the float multiply in a register, and imul adds a call |
| one closure per draw instead of two | 0.99x |
| a batched fill, one call for the whole array | 1.00x |

V8 inlines the inner closure completely, so the shipped form is already the
fast one. What is left is two transcendentals a draw at ~57 ns, and the only
ways past that change the answer: using BOTH Box-Muller outputs consumes the
stream differently, and the GPU form in `probe-gpu-gaussian.js` - 7.5x, jumped
LCG, same stream to 6.45e-6 - is f32 where the host is f64.

🔴 **SO THIS ONE IS A PRODUCT DECISION AND NOT AN OPTIMISATION, which is what
the probe's own header says.** Either GPU form means a given seed names a
different structure than it does today. Worth 4.7% of a fold, and not worth
taking without somebody deciding that seeds may be re-mapped.

### Tried and refused: splitting the diffusion attention's value product

At 256 tokens `attend` is the largest pass in a denoiser call by a wide margin -
**8.05 ms a step, 17% of the profile, more than double `qkvg`** - and its last
loop looks like an obvious mistake:

```
for (var d = local; d < DIMENSION; d += 256u) {   // DIMENSION is 48
  for (var j = 0u; j < TOKENS; j += 1u) { ... }   // 256, serial
}
```

**Forty-eight invocations of two hundred and fifty-six do the work**, each
walking every token in order. Splitting the token axis as well - one lane per
(channel, part), `floor(256/48) = 5` parts - makes the loop `TOKENS/5` deep.
Built, and it is a **small loss**:

| | `attend` | fold, 256 tok / 200 steps |
|---|---:|---:|
| as shipped | 51 ms | 10.4755, 10.5005 s |
| value split 5 ways | 53 | 10.5195, 10.5580 |

🔴 **BECAUSE PER-WORKGROUP OCCUPANCY WAS NEVER THE CONSTRAINT.** `attend`
dispatches one workgroup per (query, head): at 256 tokens that is **4096
workgroups of 256 lanes, 1.05 million threads on a device that holds 221,184**.
It is oversubscribed **4.7x already**, so lanes idle in one workgroup are
backfilled by another and the warps that exit early cost nothing. A lane-utilisation
argument is only worth making when the device is not already full.

🔴 **AND IT IS NOT BANDWIDTH EITHER, which the same arithmetic disposes of.**
k and v re-read once per query row is 9.7 GB a step - but k and v for one block
are 0.79 MB each, so all of it lives in this card's 40 MB of L2. What is left is
0.6 TFLOP/s against ~19 available: `attend` is **latency bound**, on barriers and
dependent chains, exactly as the note on its subgroup reductions says.

The untested lever that follows from that is the opposite of the one tried:
**more queries per workgroup**, which amortises the key staging and its barriers
instead of spreading one query over more lanes. At four queries a workgroup both
phases would use ~all 256 lanes (4 x 64 dots, 4 x 48 outputs) and the k tile
would be staged once for four. Not built.

### Tried and refused: sizing the pair-logits cache to the device

`PAIR_LOGITS_CACHE_BYTES` is a hardcoded 64 MiB deciding how many of the
twenty-four blocks keep their pair attention bias. The logits are `64 * tokens^2`
bytes a block, so it caches all twenty-four at 208 tokens, **sixteen at 256 and
one at 544** - a cliff that grows with length, which is the same shape as the
64 MiB cap that was costing AF2 4.65x (docs/AF2.md). Replacing it with what the
memory budget has left unclaimed was the obvious matching fix. Measured, paired,
order alternating:

| | 64 MiB | device-derived | |
|---|---:|---:|---:|
| 256 tokens (16 -> 24 blocks), 3 pairs | 10.4625 / 10.5040 / 10.4975 | 10.4385 / 10.4595 / 10.4840 | +0.26% |
| 544 tokens (1 -> 24 blocks), 2 pairs | 11.7120 / 11.6790 | 11.6965 / 11.6760 | +0.08% |

🔴 **AND THE CLIFF IS NOT WHERE THE TIME IS, WHICH THE 544 ROW SETTLES.** Going
from ONE cached block to all twenty-four buys **0.08%** - less than the 256-token
case where the cliff is shallower. Peak memory is identical to the megabyte in
every arm, so the cache is neither costing nor buying anything at these sizes.
Reverted: the constant stays, because replacing it adds a function and an import
for a result indistinguishable from zero.

The general rule this file has been applying holds - a limit that picks a
different ALGORITHM is a bug, and the OPM one was - but it does not follow that
every hardcoded byte count is worth replacing. This one and
`TRANSITION_CHUNK_TARGET_BYTES` were both measured and both left alone.

## The decoder's start, and the worst kernel in the model

With the transformer's projections split, the largest single pass in a denoiser
step was the atom decoder's `start` - **1.89 ms in ONE dispatch**, 10% of a
step. It looked like this:

    for (var c = 0u; c < C; c += 1u) {
      for (var d = 0u; d < C_TOKEN; d += 1u) { value += ... }
    }

🔴 **ONE THREAD, ONE ROW, AND 98,000 MULTIPLY-ADDS INSIDE IT.** C is 128 and
C_TOKEN is 768, so a thread walked the whole projection for its row; a
1632-atom structure ran on **1632 threads in 26 workgroups**. That is under 1%
occupancy on a 108-core device, and it measured **0.17 TFLOP/s** - an order of
magnitude below anything else in this file.

Splitting the channel out of the loop gives `QUERY_ROWS x C` invocations,

## Hoisting the conditioning norm out of the block loop

Whatever the K split was worth, this is worth doing on its own terms: the
conditioning's mean and variance **do not depend on the block**. Only the scale
does - `SingleCondLayerNormScale`, and a separate one for the transition - so
`(cond - mean) * inverse` is one tensor for the whole call, and it was being
derived **24 blocks x 2 kernels x 3 channel splits = 144 times**, by workgroups
each running two barrier-tree reductions to get it.

It now runs once, as `cond-norm`, beside the pair norm that was already hoisted
for the same reason. (The pair norm holds for a whole schedule; this one moves
with the noise level, so it is per call.)

## The sample dimension, as a second path

Built at the transformer, off by default, and the design constraint was that
**the one-sample path must not move at all**. It does not:
`tools/gpu/check-difftx-samples.js` generates every shader at `samples: 1`
against a build with the parameter absent and requires them identical character
for character, across four arms - plain, split-K, norm-split, everything at
once - and fifteen shaders. A fold gate would catch a wrong kernel; it would
not catch a slower one, and this stack's history is of changes that were
correct and cost 20%.

Above one sample the row axis becomes `(sample, token)` and three things have to
know:

- **the conditioning is per TOKEN**, one tensor for every sample - which is the
  batching win, since a weight read and a conditioning read now serve S rows;
- **the pair bias likewise**, so a query row reduces to `i % TOKENS` before
  indexing it;
- 🔴 **and attention must not cross a sample.** Every other kernel batches for
  free on a wider row axis. `attend` does not: left alone it would attend across
  samples, which is not a slower answer but a different model. Its keys are
  bounded to `(i / TOKENS) * TOKENS`.

`tools/gpu/check-difftx-batched.js` is the test that catches all three, and the
only honest one: given S copies of one activation, every sample must come back
identical to the others AND to what one sample alone produces. Both failures
above are invisible at S=1 because at one sample they are the same expression.
**relRMS 0 at S = 1, 2, 4 and 8**, against one sample and between samples.

What it is worth, at 68 tokens, medians of five:

| samples | unbatched | batched | |
|---:|---:|---:|---:|
| 2 | 24.20 ms | 16.10 | **1.50x** |
| 4 | 47.20 | 26.80 | **1.76x** |
| 8 | 92.80 | 45.70 | **2.03x** |

🔴 **AND THE HEAD CANNOT DRIVE IT YET.** The atom encoder, the atom decoder and
the sampler's positions and noise all still assume one sample, so nothing user
facing can ask for S > 1. What is done is the 61% of a step that is the
transformer, proven correct and measured; what is left is the plumbing around
it.

## Item 9 was right for AF3 and wrong for ESMFold2, and the reason is the width

Item 13 was blocked on item 9's question - whether a transition can be taken
off the fused kernel without paying the two intermediates the fusion exists to

is one number.

**Where ESMFold2's trunk actually is**, 300 tokens, 24 blocks, staged f16, by

**The same transition, three ways.** The fused kernel is

🔴 **SO SPLITTING IS A WASH AT 128 CHANNELS AND 2x AT 256, BEFORE ANY MATRIX

intermediates it would add, and at AF3's width that is the right call - there

already losing to two plain GEMMs by a factor of two.

🔴 **AND THE MECHANISM IS THE THING THE FUSION IS FOR.** What the fused kernel
holds in workgroup memory is the WIDENED row: `2 * channels * factor` floats.
At 128 channels that is 4 KB and the row tile is 16; at 256 it is 8 KB and the
tile collapses to 4, taking with it the weight-read amortisation the tile
exists to buy - 8:128 measures 21.2 ms against tile 4's 16.07, and 16:256 is
36.2. Per row: AF3 28.5 ns, ESMFold2 178.6 ns for exactly four times the work,
which is **1.57x worse per multiply-add**. The fusion's cost scales with the
channel count and its benefit does not, so there is a width at which it stops
paying and 256 is past it.

**What that is worth.** 419.88 -> about 143 ms on the trunk's largest kernel,
which is 744 -> 467 ms of GPU, **1.59x on an ESMFold2 trunk** - and the trunk
is 85% of a 300-token fold. It is the largest single item left in this file.

### The shape of the build, as it was reasoned before it was built

Three passes, not two. The first GEMM's epilogue would
have to pair column `i` with column `i + hidden` to fuse the swish gate, and
those are 1024 columns apart - different workgroups at any block width - so the
gate is its own elementwise pass. It reads 2*hidden and writes hidden, 553 MB
at 300 tokens, about 0.36 ms against an 11 ms saving. Both intermediates are
chunked over rows the way `transitionChunkRows` already chunks AF2's; that
kernel is the template, because AF2's transition is the one this repository
has already taken off its fused form and onto `createStagedMatrixShader`.


## Where AF3's device memory actually is, which is not where item 14 looked

Item 14 proposed carrying AF2's `releaseScratchSince` discipline - which took
its peak from 11.3 to 7.2 GiB - to AF3 and ESMFold2, and said to measure first.
Measured, at 400 tokens over 8 pairformer blocks with 4 template slots
(`bench-trunk.js`, which reports `deviceMemory`):

    peak 575.0 MiB, and the labels holding it at that moment:
      af3-template.scratch    195.3 MiB   five pair-sized, CHANNELS = 64
      af3-template.pair        78.1
      af3-template.output      78.1
      af3-template.readback    78.1
      af3-template.act         39.1
      af3-template.summed      39.1

**508 MiB of a 575 MiB trunk is one stage, and it is not the pairformer** - the
pairformer's own weights are 66 MiB of that peak. So the item as written was
looking in the wrong place, and the pairformer's scratch discipline is fine.

🔴 **AND IT IS AN ORDERING PROBLEM, NOT A MISSING RELEASE.** The embedder
allocated every buffer up front and freed them in one `finally`, so its five
pair-sized scratch tensors - dead the moment the last slot accumulates -
coexisted with `output` and `readback`, which are not needed until after that.
Nothing was leaking; two sets of tensors that never overlap in use were
overlapping in time.

🔴 **AND THE SUBMIT IS WHAT MAKES THE RELEASE LEGAL, which is the part that is
not obvious.** This allocator does not pool, so `release()` destroys - and
destroying a buffer that an encoded-but-unsubmitted pass still names is a
use-after-free WebGPU reports at submit time and not before. The stage is one
command buffer, so the scratch cannot be released inside it. It is two now: the
slot loop and its blocks, then a submit and the release, then the output
projection and its copy.

    peak                575.0 -> 555.3 MiB
    template stage        316 ->   245 ms   (three runs: 248, 247, 244)
    trunk, whole         1496 ->  1435
    fold                pLDDT 85.8, geometry identical

The peak falls by less than the stage does, because removing the template as
the peak just promotes whatever was second: **the MSA stack's five pair-sized
scratch tensors, 390.6 MiB at 400 tokens**, which is now the top holder in the
trunk and the next place to look. The template stage getting 22% faster is
reproducible across three runs and is not explained here; it is not the reason
for the change.

**ESMFold2 needs none of this.** It allocates one set of scratch for the whole
24-block loop and releases it after, which is the discipline item 14 was
proposing to add. Its peak at 300 tokens is 445.8 MiB, or 517.8 with the split
transition's chunked intermediate.


## The triangle projection on the units, and the width rule that keeps it off AF3

With the transition split, `tri.project` was the top of an ESMFold2 trunk's
profile - 130.6 ms of 494. It is a dense projection over a materialised source,
which is the shape docs/A100.md's GEMM rule actually governs; the kernel that
rule ruled out is `tri.contract`, whose K is the protein's length.

🔴 **AND IT NEEDS NO NEW MEMORY, WHICH THE TRANSITION'S SPLIT DID.** Its source
is the layer-normed pair and its two outputs are `a` and `b` - all three
pair-sized scratch the track already holds. Nothing is materialised that was
not materialised before.

🔴 **THE FOUR MATRICES ARE ONE GEMM WITH INTERLEAVED COLUMNS.** `projectAB`
contracts a, a's gate, b and b's gate over one read of the source and gates them
pairwise. A staged matmul's epilogue can only reach the columns inside its own
subgroup's flush block, so the four roles of channel `h` are packed as columns
`4h..4h+3` - always inside one block, whatever the geometry, because four
divides every flush width this uses. `AB_INTERLEAVED` in
src/triangle/weights.js transposes and interleaves in one pass at pack time and
**replaces** the four separate matrices, so a bundle costs no extra bytes and
only one of the two kernels is compiled for a block. The store stays
channel-major, because `tri.contract` reads it that way.

    tri.project over 8 blocks    vector    matrix   speedup
      128 channels (AF3)          33.96     31.01      1.10
      256 channels (ESMFold2)    130.55     85.59      1.53

    ESMFold2 trunk, GPU:  743.8 -> 494.0 (the split) -> 448.8   1.66x total

🔴 **IT COSTS ACCURACY, AND THE UNITS ARE WHY.** The units multiply BOTH
operands in f16, where the vector kernel's f16 mode narrows only the staged
activation and keeps the weights in f32. On `check-af3-block-any.js`'s
uniform-noise input, one block at 40 tokens:

    vector, staged f32                     1.4e-5
    vector, staged f16 (the shipped path)  2.7e-3
    matrix                                 2.0e-2

flat in the token count - 2.2e-2 at 16, 1.6e-2 at 64 - so it is the operand
rounding and not the contraction's length. There is no mitigation: this device
offers no f32 matrix configuration at all.

🔴 **SO IT IS OFF BELOW 192 CHANNELS, AND THE FOLDS ARE WHAT JUSTIFY IT ABOVE.**
At AF3's 128 it is 0.7% of a trunk for that error and the default declines it -
the same shape of rule `TRANSITION_SPLIT_MIN_CHANNELS` carries, for a different
reason: that one trades memory and this one trades precision. Where it does
apply, the block figure is not the evidence - that input is uniform noise,
which docs/AF3.md already records as harsher than a real pair representation -
the folds are:

    ESMFold2   CA-CA median 3.80480 -> 3.80483, contact precision 1.000 either way
    OpenDDE    CA-CA 3.6705 -> 3.6708, pLDDT 92.0503 -> 92.0508
    AlphaFold 3   declines it; pLDDT 85.8 and geometry identical either way

🔴 **AND THE TWO KNOBS WERE BRIEFLY ONE, WHICH IS ITS OWN LESSON.** Deriving
`triangleProjectMatrix` from the transition's config made it silently inert
whenever `pairTransitionSplit` was false - which is exactly the arm a checker
isolating the two reaches for, and it reads as "the kernel changes nothing"
rather than as "the flag did nothing". Three arms of a sweep returned the
identical figure to sixteen digits before that was noticed.

### And the output projection, which is two GEMMs and not one

`tri.project-out` is `logistic(z . Wg) * (x . Wz)` - two contractions over two
DIFFERENT sources, the layer-normed pair and the normalised contraction. No
column trick makes that one GEMM: interleaving, which is what worked for a/b,
would still need both sources staged at once.

🔴 **SO THE GATE IS ITS OWN PASS AND THE PROJECTION READS IT BACK.** Two staged
sources with two accumulator sets fits the workgroup budget and then spends
about 128 registers a lane on the accumulators; `outputModulate` - one global
read at the output cell the store is about to write - costs no registers at
all. And it needs no new memory either: at that point in the track `scratch[2]`
and `scratch[3]` are both dead, so the gate lands in one of them.

    tri.project-out over 24 blocks       vector    matrix
      fused                              106.47
      gate + modulated projection                  63.92   1.67x
        (25.67 gate, 38.25 projection)

    ESMFold2 trunk, GPU:  743.8 -> 494.0 -> 448.8 -> 406.0     1.83x

Its two matrices are stored output-channel-major and a staged matmul reads
K x N, so the same pack that interleaves a/b transposes these - a reshape, same
element count, done once at pack time.

**Checked** against the vector kernel at relRMS 1.1e-4 (256 channels) and
1.3e-4 (384), in its RESIDUAL form from a non-zero target, because a residual
that writes agrees with one that adds whenever the target starts at zero. The
folds are unchanged: ESMFold2 CA-CA median 3.80502 with contact precision
1.000, OpenDDE 3.6708 at pLDDT 92.0507, AF3 85.8 and geometry identical.

### The geometry those four share, which had never been swept in situ

At 406 ms the top four kernels were within 8% of each other and all four were
staged matrix GEMMs on the SAME block - 128x128x32 with 2x4 subgroups, carried
over from the sweep in `bench-evoformer-linear.js`, which measures a GEMM as a

**1.16x for a knob**, and every one of the four kernels improves at the winner.

🔴 **TWO THINGS MOVE IT AND THEY PULL THE SAME WAY.** A smaller K panel - 16

🔴 **AND IT IS THE THIRD TIME A STANDALONE BENCH GAVE THE WRONG TILE.** CLAUDE.md

### The cubic kernel, which this file's GEMM rule did not rule out after all

`tri.contract` is `out[h][i][j] = sum_k a[h][i][k] * b[h][j][k]` - one n x n by
n x n product PER CHANNEL, 256 of them, all the same shape and the same stride.
It is a BATCHED GEMM, and the batch is the dimension the vector kernel already
dispatches over.

🔴 **THE RULE SAID "THE INNER EXTENT MUST DIVIDE BY FOUR" AND THIS FILE READ IT
AS "SO THE UNITS CANNOT HELP HERE".** The inner extent is the protein's length,
which at 825 is not divisible by four, and the measured 0.95x was recorded and
believed. What the rule actually constrains is ONE OPERAND: the transposed one
walks the axis it is not stored on, so its four consecutive elements are
`columns` apart and it cannot be vec4-read. **The other one still can.** Built
with `vectorStaging` off for both, exactly as the rule implies, it is a wash:

    tri.contract over 24 blocks    vector 63.94    matrix, both scalar  64.24
                                                   matrix, one vec4     47.82   1.34x

So `vectorStaging` is per operand now, and the two directions take one each -
outgoing transposes the RIGHT operand and incoming the LEFT, and swapping them
returns a finite tensor of exactly the same shape, which is why the checker has
an arm for each and fails at 3.8e-1 when they are crossed.

**Where an ESMFold2 trunk ends up**, GPU time at 300 tokens over 24 blocks:

    original                                  743.8 ms
    + the split transition                    494.0    1.51x
    + the matrix triangle projection          448.8    1.66x
    + the matrix output projection            406.0    1.83x
    + the swept block                         349.8    2.13x
    + the batched contraction                 332.8    2.23x

    wall                                     1023.1 -> 650.5   1.57x
    peak                                      445.8 -> 517.8 MiB

and every kernel in the pair track is now on the units except three layer
norms totalling 31 ms. The profile is `tri.project` 72.2,
`pair-transition.wide` 72.2, `pair-transition.down` 57.8, `tri.contract` 47.8,
`tri.project-out` 30.5, `tri.project-out.gate` 21.3.

🔴 **AND THAT IS THREE TIMES THIS FILE'S OWN GEMM RULE HAS BEEN MISREAD IN ONE
DIRECTION.** It ruled out AF2's flash attention (wrong: a flash attention's
reuse is in its loop, not in K), AF3's fused transitions (wrong above 128
channels: the fusion's cost scales with the width), and this contraction
(wrong: the constraint is per operand). The rule is about a GEMM's staging and
it is correct about that; every misreading has been of what it implies for a
kernel that is not a plain GEMM. **Read it as a statement about one operand's
memory access, not as a verdict on a kernel.**


## The three layer norms, and what is actually left

With everything else on the units, an ESMFold2 trunk's remaining non-matrix work
is three layer norms - 31 ms of 332.8, or 9.4%. **They cannot go on the units at
all**: a layer norm is a row REDUCTION, not a contraction, and there is no hook
in a staged matmul that can see a whole row (which is also why the split
transition's normalise had to come out as its own pass). So the only question is
whether they are at bandwidth. Priced against this card's 1555 GB/s:

    tri.normalize                184.3 MB x48   10.86 ms    815 GB/s   52%
    tri.normalize-hidden         184.3 MB x48   12.25        722       46%
    pair-transition.normalize    138.2 MB x24    8.13        408       26%

🔴 **AND THE ODD ONE OUT WAS THE ONE THIS SESSION WROTE.** Two candidate causes
were obvious and both were wrong, which is the reason to write them down:

- **The reduction shape.** The transition's normalise reduced eight partials
  with a log tree - three barriers, twice over, once for the sum and once for
  the squares. The triangle's beside it writes both partials, barriers ONCE and
  has lane zero add eight numbers. Rewritten to match: **8.13 -> 10.05 ms**,
  24% WORSE. The tree is the right structure for this kernel and the serial sum
  is the right one for the triangle's, and nothing here explains why.
- **The half-word store.** The triangle's writeback owns a PAIR of channels per
  lane "so it owns the whole word they share"; this one wrote single f16
  elements, two lanes to a word. Paired: **8.13 -> 7.77 ms**, 4.4%. Real, and
  kept, and a twentieth of the gap.

🔴 **WHAT IT WAS IS THE CHUNKING, AND THE FIX TRADES WALL TIME FOR GPU TIME.**
The split transition walks the rows in chunks so its widened activation stays
bounded, and a chunk is its own dispatch: 16,384 rows is 2,048 workgroups of the
normalise, **59% of what this card holds**, six times a block. Raising the
budget (`pairTransitionChunkBytes`, in MiB):

    budget   chunk rows   normalise   wide   down    trunk GPU   wall    peak
     64 MiB      16,384        7.69   72.2   57.6        332.4  657.2   517.8 MiB
    128           32,768        6.29   70.5   46.2        318.0  667.9   589.8
    192           49,152        5.78   69.8   42.6        313.0  662.5   661.8
    512           90,000        5.14   69.2   40.9        310.0      -   see peak

The `down` pass gains most - 29% - because its dispatch is the smallest. **But
the wall does not see it**: three runs an arm give 657.2 ms at 64 MiB and 662.5
at 192, so a 6% GPU win is a 1% wall LOSS for 144 MiB. The trunk at this size is
not GPU-bound end to end, and creating 144 MiB more of buffers per recycle costs
more than the kernels save. The default stays at 64 and the knob is there for a
device with room and a longer chain.

🔴 **AND PACKING THEM IS A CLOSED QUESTION, NOT AN UNTRIED ONE.** Halving these
tensors would halve both the write and every downstream read - and
src/af3/pair-track-gpu.js has the measured table: `normalized`, `a` and `b`
packed cost the confidence head a factor of 1200 and miss the MSA block's bound
by 50x. Do not reopen it.

### Tried and refused: storing `b` transposed for the contraction

`tri.contract` is 47.8 ms at 13.9 TFLOP/s where the GEMMs beside it reach 26-31,
and the reason is that `b` is the one operand neither direction can vec4-read.
A diagnostic arm - the right memory pattern and the wrong answer, which is what
`bench-transition.js`'s `--diagnose` arms are for - priced both operands
vectorised at **33.6 ms**, a further 1.42x.

`b` is written by `tri.project` and read by nothing else, and that epilogue's
stores are strided by the channel whichever index they use - so writing it at
the transposed pair index looked free. Built, and it is not:

    tri.contract    47.82 -> 33.63    exactly what the diagnostic said
    tri.project     72.21 -> 88.33
    trunk           332.7 -> 334.6    a wash, slightly worse

The projection's store loses 16.1 ms where the contraction gains 14.2. A
transpose PASS is worse still: 184 MB a dispatch, 48 of them, about 11 ms of
bandwidth to save 14.2. Both are recorded here rather than left as an obvious
thing to try. The 14.2 ms is real and unclaimed; what would collect it is a
`tri.project` whose epilogue writes coalesced, which is a different kernel.
